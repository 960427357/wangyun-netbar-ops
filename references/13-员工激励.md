## 二、⚠️ 先看这个：两个名字几乎一样的提成方式，算出来差一倍

这是本模块**最容易配错、损失最大**的地方。系统内嵌了官方算例，我原样抄下来：

设阶梯配成 100→10%、200→15%、300→20%，销售额 260 元：

| 提成方式 | 算法 | 260 元算出 | 500 元算出 |
|---|---|---|---|
| **销售额提成** | **分段累进**（像个人所得税） | `(200-100)×10% + (260-200)×15%` = **19 元** | `10+15+40` = **65 元** |
| **销售总额提成** | **全额跳档**（够档就整笔乘） | `260×15%` = **39 元** | `500×20%` = **100 元** |

同样一条阶梯，**260 元时差 20 元（一倍多），500 元时差 35 元**。

- 想要「多卖多提、但只对超额部分加速」→ 选 **销售额提成**。
- 想要「冲到这个档位，全月都按高档提」→ 选 **销售总额提成**（成本高得多）。

**配置前必须跟老板确认这一句**：「超出部分按比例」还是「达到就整笔按高档」。选错了，月底对账一定吵。

## 三、提成方式矩阵（跟场景联动，不是固定四选一）

**这一条文档里从来没写过**：能选哪些提成方式，取决于先选了哪个「适用场景」。

| 适用场景 | 可选提成方式 | 备注 |
|---|---|---|
| 商品推销 | 固定提成 / 销售额提成 / 销售总额提成 | 可指定商品范围 |

所以：**先选场景，再看能选什么方式。** 顺序反了会发现选项对不上。

## 四、四种算法详解

### 1. 固定提成

字段变回 **「提成金额」**，单位 `元`。

```
【请输入 提成金额】元
```

每成交一单给固定金额。适合标准化商品（卖一桶泡面给 1 元）。

**适合**：商品单价稳定、想简单粗暴激励。
**风险**：卖 1 元的东西也给同样钱，亏本。

### 2. 销售额提成 —— 分段累进

字段变成 **「提成规则」**，是一个可加 100 行的阶梯表：

```
销售额累计超过【X】元部分，提成【Y】%    [删除]
+ 添加（最多添加 100 条）
```

官方算例（原样保留，这是理解算法的唯一准确依据）：

> 销售额累计超过 100 元部分，提成 10%；100(不含)-200(含) 元之间的这部分提 10%
> 销售额累计超过 200 元部分，提成 15%；200(不含)-300(含) 元之间的这部分提 15%
> 销售额累计超过 300 元部分，提成 20%；超过 300 元的这部分提 20%
>
> 500 元 → `(200-100)×10% + (300-200)×15% + (500-300)×20% = 65`
> 260 元 → `(200-100)×10% + (260-200)×15% = 19`
> 150 元 → `(150-100)×10% = 5`
> 没超过 100 元 → 不提成

**第一档的门槛是「起征点」，不是「第一段」**：配「超过 100 元部分提 10%」时，卖 150 只提 (150-100)×10%=5，**前 100 元一分不提**。

### 3. 销售总额提成 —— 全额跳档

同样是阶梯表，但文案不同：

```
销售总额达到【X】元，提成【Y】%    [删除]
```

官方算例：

> 达到 100 元(含) 提 10%；达到 200 元(含) 提 15%；达到 300 元(含) 提 20%
>
> 500 元 → `500×20% = 100`
> 260 元 → `260×15% = 39`
> 150 元 → `150×10% = 15`
> 少于 100 元 → 不提成

**够到哪一档，整笔都乘那一档的比例**。阶梯行数越多，成本越高，因为它总按最高满足档算。

### 4. 单笔充值提成 —— 只在「会员充值」场景出现

**空态只有「+添加」按钮，没有任何文案提示**，加了行才看得见结构：

```
单次充值满【X】元，提成【Y】元    [删除]
```

官方算例（注意最后一条，这是套利口子）：

> 单次充 200（含）→ 提 2 元
> 单次充 300（含）→ 提 3 元
> 单次充 500（含）→ 提 6 元
> 单次充 400 → 未达 500 档，仅满足 300 档，提 **3 元**
> **分两笔各充 200（合计 400）→ 分两单核算，每单各提 2 元，合计 4 元**

**它按「单笔」算，不按「累计」算。** 顾客把 400 拆成两笔 200，员工多拿 1 元；拆得越多拿得越多。
如果配了「充 500 提 6 元」这种大额档，员工会主动教顾客拆单，直接吃掉大额奖励。**要么别配大额档，要么配成销售额提成。**

## 五、新增弹窗字段（8 项，动态变化）

弹窗宽 800px，标题「新增提成规则」，底部只有 `保存` / `取消`。

| 字段 | 必填 | 控件 | 随什么变 |
|---|---|---|---|
| 规则名称 | 是 | 文本，**上限 50 字**，实时显示 `0 / 50` | — |
| 适用场景 | 是 | 单选：商品推销 / 会员拉新 / 会员充值 / 旺云团购 | 决定后面能选什么 |
| 提成方式 | 是 | 单选：固定提成 / 销售额提成 / 销售总额提成（会员充值多一个单笔充值提成） | **选项随场景变** |
| 提成金额 **或** 提成规则 | 是 | 固定提成→金额输入框（元）；其余三种→阶梯表（+添加，最多100条） | **字段本身会换名换控件** |
| 计算提成周期 | 是 | 单选：每日 / 自然月 / 有效期 | — |
| 生效时间 | 是 | 日期时间选择器 | — |
| 结束时间 | 是 | 日期时间选择器 | — |
| 参与岗位 | 是 | 复选：管理员 / 保洁员 / 维修工 / 收银员（多选） | — |
| 参与商品： | 仅商品推销 | 下拉：指定商品 / 指定分类 / 全店商品 | 选了「指定商品」才出现「选择商品」按钮 |
| 团购套餐 | 仅旺云团购 | 下拉（**必填**）：指定套餐 / 全部套餐 | — |

**「计算提成周期」的三种语义：**

- **每日**：每天算一次，当天清零。适合日结小激励。
- **自然月**：整月累计，月底算。适合阶梯提成（阶梯要靠累计才爬得上去）。
- **有效期**：按规则的生效→结束整段算。

**坑：选「每日」+ 阶梯提成 = 每天从 0 开始爬阶梯。** 如果目的是「月销 5000 提 10%」，周期必须选「自然月」，否则永远只爬到第一档。

### 🔴 一个场景只该有一条生效规则——旧的要**手工作废**

**店方实操约束（客户确认）**：同一个「适用场景」只保留一条生效规则。
要换口径（比如把「充值提 5%」换成「满 200 提 2 元」），必须**先手工作废旧规则，再新建**。

**这不是系统自动行为，这点很容易搞错：**

- 系统**不会**在保存新规则时自动作废旧规则；
- 系统**不会**提示「该场景已有规则」；
- 所以 2026-10-30 那次「5%网费提成」进历史，是**店主自己点的作废**（怕两条同时生效出错），
  **不是**系统替换。我最初按「作废时间≈保存时刻」推成系统静默作废，**是错的**，已改正。

**没先作废就直接建第二条会怎样？—— 已实测（2026-10-31 00:04）：会被服务端拒绝。**

- 点保存后弹出 toast：**「商品规则重复」**（原文，四个字，无更多说明）；
- **弹窗不关闭、已填内容不丢**，可以改完重试；
- 表单没有行内红字报错，只看字段看不出来，容易误以为「没点上保存」。

所以顺序不能反：**先作废 → 再建**。系统不会替你作废，也不会在保存前提示冲突。

正确姿势：

1. 先去「当前规则」看同场景有没有规则；
2. 有 → 抄下它的全部参数（场景/方式/阶梯每一档/周期/起止时间/岗位/范围），
   因为作废后只剩历史列表里一行摘要，阶梯明细得点「查看」才看得到；
3. 手工作废旧的（行尾「作废」→ 确认框「**确定将选择数据作废?**」→ 点「确定」→ 提示
   「**作废成功， 可到历史规则里面查看**」）→ 建新的；
4. 建完回列表核对，并去「历史规则」确认旧那条已在里面。

历史里的「商品推销」也是同一套路：16:05 建的，16:15:23 作废，16:17 又建一条——人工操作，不是系统行为。

### ⚠️ 数值不可信：本店是测试环境

**「演示门店」是测试场所，上述 50%、1 元、5% 全是随手填的占位符，不代表任何真实经营口径。**

所以这里**不做成本估算、不发风险预警**。判断一套激励配得对不对，只用下面这个不看数值的判据。

### 判据：不看比例大小，看结构能不能被套利

真实门店里会亏钱的规则，问题几乎都出在**结构**而不是数字大小。数字可以后面慢慢调，结构错了要么改不了、要么每月持续漏钱。

| # | 结构特征 | 为什么危险 | 怎么改 |
|---|---|---|---|
| 1 | **起征点 = 1 元**（等于没有起征点） | 任何一笔销售都进入提成，低毛利单件（3 元可乐）提成可能等于全部毛利 | 起征点提到毛利之上；或改成「满 X 元才起算」 |
| 2 | **周期 = 每日 + 分段累进阶梯** | 每天清零，阶梯第二档永远爬不上去，配了多档等于只配了第一档 | 想用阶梯就必须选**自然月** |
| 3 | **范围 = 全店商品** | 成本失控，高毛利和低毛利的商品被同一个比例覆盖 | 改「指定分类」，把高毛利品类单独拉比例 |
| 4 | **岗位 = 收银员一人** | 自己卖自己提，无第二人校验，配合「全店商品」几乎无法审计 | 加店长/值班核对，或用「引导购买 vs 主动购买」看真实推销 |
| 5 | **比例 > 该品类毛利率** | 卖得越多亏得越多（**需真实毛利率才能判，测试环境无法判断**） | 先拿毛利率表核对再定比例 |
| 6 | **单笔类方式 + 可拆单** | 400 元拆两笔 200，提成从 3 元变 4 元（见 §十一 坑 4） | 用分段累进，或设单日封顶 |

**这套判据与数值无关，换到真实门店照样能用。** 数值只影响第 5 条，而那一条必须拿真实毛利率来判。

### 上真实环境前必须重新确定的 6 个数

测试环境的配置**一个都不能直接搬**，进店要先问清这 6 项，否则等于没配：

1. 各品类**毛利率**（决定比例上限）
2. **日销 / 月销基线**（决定起征点定多高）
3. 提成周期到底按**日**还是按**自然月**
4. 参与**岗位**（是否只有收银员）
5. 商品范围是**全店**还是**指定分类**
6. 每月提成**预算总额**（倒推比例，比正着算可靠）

- `充值规则`：100→1%、300→3%、500→5%、1000→10%、2000→20%，标准**分段累进充值激励**；大额 50000→50% 是防拆单的封顶档。
- `旺云团购推销`：200→3% 到 2000→6%，四档爬坡 + 指定 3 个套餐，正经的券推销激励。
- `商品销售总提成`：门槛 10000 元提 3%，「冲月量」玩法。
- `奶茶提出`：固定 1 元/单 + 指定商品 3 个 —— **指定商品 + 固定金额**，最适合高毛利单品。
- `会员拉新奖励`：固定 10 元/人 —— 印证了 **会员拉新只能配固定提成**（系统只给这一个选项）。

**注意：以上数值本身也是历史遗留/测试填的，别直接抄。** 要抄的是结构：
`有起征点` + `分段累进` + `自然月` + `指定商品/分类`，这四件事凑齐才是能跑的激励。

（当前那两条「超过 1 元就提」之所以显得粗糙，正是四件事一件都没做 —— 这是**结构问题**，与填了 50% 还是 5% 无关。）

## 十一、坑清单

| # | 坑 | 后果 / 对策 |
|---|---|---|
| 1 | 销售额提成 vs 销售总额提成名字太像 | 260 元时差 19 vs 39 元。配错必吵，先确认口径 |
| 2 | 提成方式选项随场景变 | 会员拉新只有固定提成；单笔充值提成只在会员充值。先选场景 |
| 3 | 「提成金额」和「提成规则」是**两个不同字段** | 切方式时字段会换名换控件，别照着模板填 |
| 4 | 单笔充值提成按单笔算 | 拆单套利：400 拆两笔 200，提成从 3 变 4 元 |
| 5 | 第一档门槛是起征点 | 「超 100 提 10%」时卖 150 只提 5 元，前 100 不提 |
| 6 | 每日 + 阶梯 = 阶梯永远爬不上去 | 想按月冲量必须选「自然月」 |
| 7 | 单笔充值提成空态只有「+添加」，无任何文案 | 不点添加看不出结构，容易以为坏了 |
| 8 | 「查看」弹窗里单选/复选显示的是**全部选项**，不是已选值 | 只能看列表行的「参与岗位」列判断，别被弹窗误导 |
| 9 | 弹窗残留 | 连续点两行的「查看」，第二次可能读到上一条的数据。**每读一条要重载页面** |
| 10 | 结算 T+1 | 今天的单明天 8 点才进明细，当天对不出数是正常的 |
| 11 | 结算记录有 8 列被隐藏 | 需要明细（规则、销售额、销量）时，这些列在 DOM 里，可以抓 |
| 12 | 「作废」有二次确认（**已实测**） | 确认框文案「确定将选择数据作废?」，按钮「取消 / 确定」；成功后 toast「作废成功， 可到历史规则里面查看」，行从当前规则消失、进历史规则 |
| 13 | 「提成规则」这段文字后面拼了一整段**示例阶梯**（100/10%、200/15%、300/20%） | 用脚本解析真实阶梯时必须先按「提成规则示例」切掉，否则每条规则都会被多读出 3 档假数据，估算全错 |
| 14 | 会员拉新**只有固定提成** | 想按充值额比例奖励拉新，产品不支持，只能给人头费 |
| 15 | **生效时间必须晚于「当前时刻」，不能填当天 0 点** | 点保存弹「生效时间不能小于当前时间」，规则不会创建。想「今天开始」也得填未来时间（如今晚 23:59 或明天 00:00）。已实测踩到 |
| 16 | **改单选（场景/方式/周期）会把已填的日期清空** | 表单会重渲染。顺序必须：名称 → 场景 → 方式 → 周期 → 阶梯 → 岗位 → **日期最后填**。日期填早了会静默变空，保存时才报错 |
| 17 | 「新增」按钮文案是「新 增」（两字中间有空格） | `has-text("新增")` 匹配不到，会 30s 超时。用 `hasText: /新\s*增/`；「保 存」「取 消」同理 |

## 十二、配置 SOP（从 0 配一套激励）

0. **先确认这是真实门店还是测试场所。** 看右上角场所名，或问客户。**测试环境不要配真实规则**，
   也**不要拿测试环境里的现有规则当参考值**（那些数字是随手填的）。真实门店才往下走。
1. **先定口径**（找老板确认，写成一句话）：
   - 激励什么？商品推销 / 会员拉新 / 会员充值 / 旺云团购
   - 给谁？哪些岗位
   - 按件、按比例、还是按阶梯？比例是「分段」还是「整笔跳档」？
   - 多久算一次？每日 / 自然月 / 整段有效期
2. **算一遍成本**：拿历史日销/充值数据代入，算出每天、每月要发多少。**超过毛利就别配。**
3. 当前规则 → 新增 → 字段按 §五 填，注意字段会随场景/方式变化。
4. 保存后回列表核对「参与岗位」「参与商品」列显示是否正确。
5. 第二天早上 8 点后看「提成结算 → 未结算提成」有没有涨，验证规则真的在跑。
6. 月底确认结算设置：自动结算开关是否要开、结算方式（现金/微信/支付宝/银行卡）。

**排查「配了但没提成」的顺序**：规则生效时间是否已到 → 结束时间是否已过 → 参与岗位里的人是否真的在岗 → 商品范围是否覆盖卖的东西 → 计算周期是否到了结算点 → 未结算提成是否 T+1 才有数。

## 十三、脚本

`scripts/audit-commission.js`：只读审计。把当前 + 历史规则全部读出来，展开每条阶梯值，
并对当前规则做**结构体检**（起征点 / 每日×多档 / 全店范围 / 仅收银员 / 可拆单）。

输出里的 `risks` **只列结构问题，不因数值大就报警**；`estPerDay/estPerMonth` 是基于 `ASSUME` 的线性外推，
`ASSUME` 默认值是占位假设，**不是真实经营额**。要判断「比例是否吃掉毛利」，必须先把
`ASSUME.grossMarginPct` 填成真实毛利率，否则脚本会明确输出「未判」，不要拿它下结论。
