## 一、结论先行

1. 商超是三层：**基础管理（主档）→ 商品管理（库存与销售）→ 团购/核销（线上渠道）**。主档没建，商超里没有商品可卖。
2. 主档顺序：**商品分类 → 商品名称 → 计量单位 → 吧台设置 → 标签设置 → 库存预警**。分类为空时新增商品存不进去。
3. 库存有四个数：默认吧台库存、未出货、总库存、以及各吧台分库存。**纯上架只动前两个，不动总库存**（这是踩过的坑）。
4. 核销收入有两种统计口径（平台展示价 / 订单交易价），选错会让账面和平台对不上。

#### 2.2.1 库存预警 `baseManage/warning`（2026-11-02 实测）

> 需求：「库存低于 X 就提醒我」。三块 tab **按分类 / 按商品 / 按材料**，结构完全相同，
> 区别只在关联对象是分类、商品还是原料。给原料设预警走**第三块「按材料预警」**。

**列表列**：材料名称（或类别名称 / 商品名称） / 最低阈值 / 状态 / 短信预警 / 操作。
**按钮**：顶部「添加」（部分 tab 顶部还有「保 存」），行内「保 存 / 删除」。

**添加弹窗字段**（按材料预警实测）：

| 字段 | 控件 | 说明 |
|---|---|---|
| 材料名称 | 下拉单选 | 选项来自原料管理，如「红牛原料」 |
| 最低阈值 | 数字输入 | 库存**低于**该值时触发，单位随材料走（罐 / 袋 / 瓶） |
| 短信预警 | 开关 + 「请输入手机号」 | 开关打开后才出现手机号输入框 |

🔴 **弹窗点「保 存」不等于落库。** 点完弹窗关闭，表格里出现的是**可编辑态的行**，
该行右侧还有一个「保 存」，**必须再点一次才真正写库**。只点弹窗保存的话，接口没有任何请求，
刷新页面数据就没了。这是本页最容易踩的坑，第一次配会以为已经成功。

**新增行默认 `status=0`（状态列显示「关」）**，预警不生效，要手动打开行内状态开关再保存。

**接口**：

| 用途 | 接口 | 说明 |
|---|---|---|
| 读列表 | `GET /business-erppro/stockConfig/list` | 明文 JSON，含全部配置项 |
| 写配置 | `POST /business-erppro/stockConfig/edit` | 成功返回「操作成功」 |

**记录字段**（实测一条材料预警）：

| 字段 | 示例值 | 含义 |
|---|---|---|
| `name` | 红牛原料 | 对象名称 |
| `number` | 20 | **最低阈值** |
| `mobile` | 18060783837 | 短信接收手机号 |
| `status` | 1 | 1 = 启用，0 = 关闭 |
| `isMobileWaring` | 1 | 1 = 短信通道开 |
| `isWwbWaring` | 1 | 1 = **旺旺吧 APP 推送开** |
| `type` | 2 | 0/1/2 对应 分类 / 商品 / **材料** |

🔴 **读开关状态别读错列。** 表格第 0 列是行选择框（`input[type=checkbox]`），不是状态开关。
状态在 `td` 内的 `.el-switch`，判据是 `className.indexOf('is-checked') >= 0`（绿色为开）。
曾经把行选择框当成状态读，误判「开关没打开」，实际早就开了。

**两套提醒通道，互相独立**：

| 通道 | 开关 | 前置条件 | 费用 |
|---|---|---|---|
| 短信 | `isMobileWaring` + 全局「短信预警」总开关 | **短信余额 > 0**，否则空转 | 按条计费 |
| APP 推送 | `isWwbWaring` | **通知设置里给对应岗位勾「商超补货通知」** | 免费 |

- 顶部**全局「短信预警」总开关**默认是**关**的，关着时材料级配了手机号也发不出。
- **短信余额 0 条是常态**（`基础设置 → 系统设置 → 短信管理 → 购买短信` 实测国内/国际均 0，从没买过）。
  此时不要下「预警不可用」的结论——**切 APP 推送即可，不用花钱**。
- APP 推送的接收人**不是手机号，而是岗位**。手机号填的是一个具体账号时，要确认该账号属于哪个岗位，
  再去 `通知设置` 给那个岗位勾权限。详见 `05-员工权限.md` §十一。
- 短信模板文案是**商品**口径，材料预警也套用同一条模板，收到的会是「……商品【红牛原料】当前库存不足……」，
  不是发错。

**APP 推送要客户端配合**：目标账号需登录「旺旺吧网吧版」APP，并在手机系统里允许通知权限。
这一步在后台做不了，配完要让对方确认收到过测试推送。

**设置完成后怎么验收**：`GET /business-erppro/stockConfig/list` 里应出现该记录，
`status=1`、`isWwbWaring=1`、`number` 是设定阈值；再回 `通知设置` 页面确认目标岗位的
「消息通知类型」列里带上了「商超补货通知」。

#### 2.2.2 商品标签 / 标签设置 `baseManage/tagsSet`（2026-11-02 实测）

> 需求：「给商品打个标签」。🔴 **这里的「标签」不是营销标签、不是分类标签，是规格选项组**
> ——接口名直接暴露了真相：`goodsSpecsCategory`（规格分类）。它决定顾客下单时**要选什么**。

**列表结构**：标签名 / 选项值（顿号连接）/ 操作（编辑 删除）。按钮「添加」。
现有 4 条（含实测新增 1 条）：

| 标签 | 选项值 | 说明 |
|---|---|---|
| 甜度 | 全糖，七分糖，半糖，三分糖，不加糖 | 不加价 |
| 温度 | 热，常温，去冰，正常冰，加冰 | 不加价 |
| 茶水 | 龙井(+￥15)，绿茶(+￥10) | 选项带加价 |
| 测试标签 | 常温，冰镇(+￥2) | 实测建的，可删 |

**添加弹窗**（标题「添 加」）只有两个字段：

| 字段 | 控件 | 限制 |
|---|---|---|
| 标签 | 文本输入 | `maxlength=10` |
| 标签内容 | 动态行：选项名（`maxlength=10`）+ 价格（选填，`number`） | **最多 5 个**，点「添加」加一行 |

带加价的选项在列表里显示为 `名称(+￥N)`，不带价只显示名称。

**它跟商品的关系**：

- 入口在商品入库 / 编辑弹窗的「**商品标签**」字段，**普通商品**与**自制商品**才有，
  权益商品 / 网费没有这个字段。
- ✅ **可以多选，一个商品能同时挂多个标签组**（2026-11-02 实测：同一商品挂「甜度 + 温度 + 测试标签」
  共 3 组，保存 `POST goodsInfo/edit` 返回 200，回读 `specsInfo` 确实是 3 个对象）。
  下拉里每个选项显示为 `标签名（选项1, 选项2…）`，**点选后下拉不自动关闭**，可连续勾；
  已选的每组渲染成一个 `.el-tag`，各带一个关闭图标，可单独移除。
- ✅ **顾客购买时，每个标签组内单选**（选了甜度就只能在 5 种糖度里挑 1 个，不会同时要全糖又要半糖）。
  也就是说：**商品 → 标签组 是多对多，顾客 → 每组选项 是单选**。
- 换标签不等于覆盖：多选语义下，取消某个 `.el-tag` 只移除那一组，其余保留。
  但把商品从一个标签换到另一个仍要手动加新的、删旧的，**旧组不自带加价就会一起失效**。

> 🔴 **判断单选/多选别看 CSS 类，要看行为。** 我曾用 `.el-select` 是否有 `is-multiple` 类、
> 当前 `.el-tag` 数量来判，得出「只能挂一个」的错误结论——而实际这个组件是多选，
> 只是当时那个商品恰好只挂了 1 组。可靠判据只有三条：
> ① 选中后 `.el-tag` 是否累加；② 下拉是否自动关闭（多选不关）；
> ③ 是否存在多个 `.el-tag__close`（多选才有）。

**接口与数据结构**：

| 用途 | 接口 |
|---|---|
| 读全部标签 | `POST /business-erppro/goodsSpecsCategory/getSpecsCategoryList`（明文 JSON） |

```json
{
  "id": "2117157111833174018",          // 标签组 id（= specsCategoryId）
  "name": "测试标签",
  "placeId": "51130210900163",
  "goodsSpecsResults": [
    { "id": "2117157111841562625", "specsValue": "常温", "specsPrice": "" },
    { "id": "2117157111841562626", "specsValue": "冰镇", "specsPrice": 2.0,
      "specsCategoryId": "2117157111833174018" }
  ]
}
```

🔴 **选项价格留空存的是空字符串 `""`，不是 `0.00`。** 实测：建「常温」时价格没填 → `specsPrice: ""`；
「冰镇」填 2 → `specsPrice: 2.0`。而历史标签（甜度/温度）的选项都是 `0.0`。
留空的选项在列表里不显示 `(+￥)`，但**参与计算时是否按 0 处理没有验证**，批量建标签时建议显式填 0。

**商品侧的关联字段**（`GET /business-erppro/goodsInfo/getInfoList`）：

| 字段 | 值示例 | 含义 |
|---|---|---|
| `status` | 1 | **1 = 上架**、0 = 下架 |
| `clientSale` | 1 | 允许网民自助购买（1 是 / 0 否） |
| `attribute` | 0 | 0 普通 / 1 自制 / 2 权益 / 3 网费 |
| `salePrice` / `buyingPrice` | 1.0 / 0.0 | 销售价 / 进货价 |
| `totalAmount` | 10 | 总库存 |
| `barList` | `[{barNum:10, barName:"默认吧台"}]` | **各吧台库存，这里才是「上架到哪」** |
| `specsInfo` | 数组 | 挂的标签组及其选项 |

#### 2.2.3 上架到底是什么意思：填「上架吧台」数量

🔴 **商品入库弹窗里的「上架吧台」就是上架动作**，不是列表里那个「下架」按钮。
填了出货数量，商品才会进吧台库存、才会在收银台和客户端卖得出去。

商品入库弹窗完整字段（选完分类/名称/单位后才会全部出现，**2026-11-14 起 17 项**）：

| 顺序 | 字段 | 说明 |
|---|---|---|
| 1–4 | 商品分类 / 商品属性 / 商品名称 / 商品单位 | 前三项决定后续字段是否出现；右侧都有「添 加」，现在**内嵌展开**（§2.2.4） |
| 5 | 商品条形码 | 选填 |
| 6 | **商品标签** | 可挂多个标签组，见 §2.2.2 |
| 7 | 允许网民自助购买 | radio：是(1) / 否(0)，**默认都不选** |
| 8 | 兑换所需积分 | 填了就生效，无需开换购 |
| 9–10 | 进货价 / 销售价 | 默认 `0.00`。🔴 入库仍不落销售价，回「编辑」设 |
| 11 | 销售时间 | 选填 |
| 12–13 | 开启换购 / 允许会员网费购买 | switch |
| 14 | 数量 | 本次入库总量（进仓库） |
| 15 | **总未出货库存** | **新增，只读**，当前仓库里还没出货的数量 |
| 16 | 上架吧台 | 上架数量 |
| 17 | 出货到默认吧台（0） | 出货数量，这一步才是真正进吧台可售 |

> 🔴 14 / 16 / 17 三个数量是分开的。入库量进仓库，出货量才进吧台。
> 只填「数量」不填出货，商品在仓库里，收银台卖不出去，列表会显示在「未出货」列。

保存接口 `POST /business-erppro/goodsInfo/goodsWarehousing` → `code 200 操作成功`。

**实测一条完整链路**（2026-11-02）：

1. 基础管理 → 商品名称 → 添加「测试标签商品」（`POST goodsName/add`）
2. 标签设置 → 添加「测试标签」= 常温 / 冰镇(+￥2)
3. 商品管理 → 商品入库：分类=饮料、属性=普通商品、名称=测试标签商品、单位=杯、
   标签=测试标签、自助购买=是、销售价=1、数量=10、上架吧台=10
4. 结果：`status=1`、`barList=[{默认吧台:10}]`、`totalAmount=10`、
   `specsInfo=[测试标签(常温, 冰镇+￥2)]`，列表操作列变成「下架」

**判断有没有真上架，看三处，缺一不可**：

| 看什么 | 位置 | 期望 |
|---|---|---|
| `status` | 接口 | 1 |
| `barList[].barNum` | 接口 | > 0（为 0 表示只在仓库、没到吧台） |
| 操作列按钮 | 页面 | 显示「下架」（说明当前在架） |

🔴 列表页的「默认吧台库存 / 未出货 / 总库存」三列**有固定列错位**，
按 `td` 顺序读会和表头错开一格（实测表头 12 列、单元格 12 个但内容错开一格）。
要准确值就查接口 `barList` 与 `totalAmount`，别靠读列表单元格。

**两条操作经验**（2026-11-02 实测）：

- **切换「商品属性」不会清空已选内容**。选了自制商品、填好分类/名称/单位/标签后，
  改成普通商品，前面填的全部保留，只是多了「商品条形码」字段。
  与促销页「切范围即清空」的行为**相反**，别照搬那套防护。
  但🔴 **属性保存后锁死**（`el-select__wrapper is-disabled`），选错只能删了重建。
  **自制商品会扣原材料库存**，纯外购成品要选普通商品。
- **商品名称的图片用 file input 直传**：弹窗里 `input[type=file]` 一个，
  Playwright 用 `setInputFiles()` 即可；上传是异步的，**要轮询弹窗内 `img.src` 非空再点确认**，
  否则图还没传完就提交会存成无图。图片限制 jpg/png/jpeg、≤500KB。
  上传成功回填 OSS 地址，形如
  `https://upload.51yunmeng.com:9000/operation/BUSINESS_SHOP/<文件名>.jpg`。

#### 2.2.4 内嵌「添 加」：分类 / 名称 / 单位 / 标签 都不用跳页了（2026-11-14 改版）

🔴 **旧行为已作废。** 2026-11-02 之前，点分类/名称/单位旁的「添 加」会跳到
`baseManage/goodsCate` 等页面，**入库弹窗被关掉、已填内容全丢**。
2026-11-14 改版后改为**在入库弹窗内就地展开子面板**，弹窗不关、已填内容不丢。

实测四处「添 加」全部内嵌，标题仍是「商品入库」（`.el-dialog` 数量保持 1）：

#### 2.3.2 🔴 口径（页面原文，答之前必须念）

> **（不包含使用会员余额支付、核销和积分兑换的订单，套餐和未填写进货金额的商品订单进货金额按 0 元进行计算）**

拆成三条能用的结论：

1. **会员余额支付、核销、积分兑换的订单不计入销售收入。** 所以「销售金额」≈现金/第三方实收，
   不等于营业额。
2. **未填进货价的商品，进货金额按 0 计。** 于是「销售差额」= 销售额 − 0 = 销售额，
   **看着毛利率 100%，其实是假的**。毛利要可信，得先把每个商品的进货价补全。
3. 套餐的进货金额也按 0 算。

**汇总金额里剔除了「支付渠道 = 积分兑换」的行，但明细行照样显示额度。** 于是明细相加 ≠ 汇总，
差额正好是积分兑换渠道那一笔：

```
明细 404.03 − 汇总 336.03 = 68.00 = 支付渠道「积分兑换」的 68 元
```

对不上账时先查这个，不要怀疑数据丢了。脚本里的
`异常 → 明细金额合计 vs 汇总金额` 会自动把这个差额和积分兑换金额摆出来。

#### 2.3.3 🔴 时间范围：不选时间 = 当月

**时间控件显示是「-」（空），但那不代表全部数据——查询默认带的是当月区间。**

实测验证：控件文本为 `-`，而明细日期范围是 `2026-10-08 ~ 2026-10-28`，
汇总金额 336.03 又与「2026-10 月」那张卡完全相等 → **默认就是当月**。
误以为「空 = 全部」，会把一个月的量当成累计量报出去。

要换区间只有一条路：**点日期控件手选**（`.el-date-editor--datetimerange`）。

- 那 4 个 `开始日期/开始时间/结束日期/结束时间` 输入框 **`getBoundingClientRect` 全是 0×0**，
  Playwright 直接点会报 `Element is not visible` —— 要**点外层的 `.el-range-editor` 容器**，
  不是点 input。
- 页面有两套筛选表单（商品明细一套、分类明细一套），另一套是隐藏的。
  取 `input.el-input__inner` 时要按「可见」过滤，否则拿到的是隐藏那套。
- 🔴 **接口不能直连**：`getSaleDocumentTotal` / `getSaleDocumentCategorySummary` 的请求体是
  `{"param":"<RSA 密文>"}`（**响应是明文，请求是密文**），自己拼 JSON 打过去返回
  `406 非法访问`。所以查历史月份只能走 UI，或者看 ① 那 6 张月卡。

历史上只有 6 个月的月度汇总，再往前没有入口。

#### 2.3.5 读数的正确顺序（缺一步结论就会偏）

1. **先看 ① 月卡的 6 个月趋势** —— 单月 300 元和单月 3 万元，后面的解读完全不同；
2. **再看 ② 汇总**（件数 + 金额 + 积分），这是当月总量；
3. **翻完 ④ 分类明细**，看金额集中在哪个分类；
4. **翻全 ③ 商品明细**（10 条/页，必须翻页抓全量，只读第 1 页会漏掉 2/3）；
5. **对三处数**：明细件数之和 = 汇总销售数量；明细金额之和 − 汇总金额 = 积分兑换渠道金额；
6. **最后才排单品榜**，并按 `支付渠道` 剔掉 `活动赠送`（0 元）和 `积分兑换`，
   否则「卖得最好的」可能是一分钱没收到的那款。

#### 2.3.6 ⭐「销售人员」= 员工提成归属（产品方确认 + 实测交叉验证）

**一句话：这一列有名字，那个员工才参与这单的提成；空白就没人拿。**
能不能真拿到钱，还要过提成规则的门槛。产品方原话：
「有销售人名字，就有员工参与员工提成，只要员工提成有这个规矩，他就可以参与。」

**归属判据（缺一不可，六道关）**：

| 关 | 判据 | 在哪看 | 不满足会怎样 |
|---|---|---|---|
| ① 开关 | 两个「派送人」开关都开（吧台一个、客户端一个） | 基础设置 → 网吧配置 → 基础配置 | **连选人框都不出现** → 永远空白 |
| ② 在岗 | 开单时这个人在岗（有排班 / 自由打卡已上卡） | 排班 + 考勤明细 | **候选名单里没有他** |
| ③ 有名字 | 销售总览「销售人员」非空 | 本页 | 空白 → **0 人计提成**，不会自动转给操作人 |
| ④ 岗位对上 | 该员工的岗位 ∈ 规则的「参与岗位」 | 员工管理 + 当前规则 | 岗位不在名单 → 卖了也不计 |
| ⑤ 场景对上 | 规则场景 = `商品推销`（网费类走 `会员充值`、团购走 `旺云团购`） | 当前规则 | 场景不匹配 → 不计 |
| ⑥ 过门槛 | 超过起征点/档位才提 | 当前规则 | 例：超 1 元才提 50%，1 分钱的单实得 0 |

> 前两关在提成页之外，**追空白原因必须先看它们**：开关没开 → 没有选框；开单时没人在岗 → 选区是空的。
> 详见 `13-员工激励.md`「前置两关」、`15-排班与班次.md` §四（打卡两种模式）。

**实测印证（同一家店，同一时间窗）**：

销售总览的「销售人员」整月只出现过两个名字：**员工A**、**员工B**。
提成结算页的「提成明细」员工名单也正好是这两个（外加一条同名离职记录）：

| 提成明细 · 员工 | 工号 | 累计提成 | 未结算 |
|---|---|---|---|
| 员工A | `--` | ￥73.46 | ￥48.51 |
| 员工B | `--` | **￥0.00** | ￥0.00 |
| 员工A【已离职】 | 001 | ￥0.00 | ￥0.00 |

- **员工B 有销售人名字、却一分没拿到** —— 他名下那单是脉动 **0.01 元**，
  规则是「销售额累计超过 1 元部分提 50%」，**1 分钱过不了起征点**。
  → 有名字只是「进场资格」，不是「拿钱保证」。
- **两个「员工A」是两条员工记录**，提成**不合并**：在职那条 ￥73.46，离职那条 ￥0.00。
  员工离职再入职、或重复建档，提成会**断成两截**，对账时别以为是系统丢数。

**🔴 名字取的是「姓名」，不是昵称**（这是最容易认错人的地方）：

| 员工管理 · 昵称 | 岗位 | 姓名 |
|---|---|---|
| 代管账号 | 收银员 | **员工A** |
| 收银B | 收银员 | **员工B** |

所以「操作人」列显示 **收银B**（昵称），而「销售人员」列显示 **员工B**（姓名）——
**同一个人在两张列里叫不同名字**。对不上人时去员工管理看「姓名」列，别看昵称。

**🔴 岗位只勾了「收银员」→ 管理员在吧台开单没有提成。**
本店当前规则参与岗位`收银员`，而管理员（管理员A / 管理员B / 管理员C）虽然也在开单，
他们卖出去的单**不计提成**。要发管理员的提成，得先把岗位加进参与岗位。

**🔴 实测：86.6% 的销售额没有销售人，等于没有任何人能拿提成。**

按「销售人员」聚合当月 336.03 元：

| 销售人员 | 件 | 元 | 笔 | 占比 |
|---|---|---|---|---|
| **（空白）** | 22 | **291.01** | 12 | **86.6%** |
| 员工A | 28 | 113.01 | 17 | 33.6% |
| 员工B | 1 | 0.01 | 1 | 0.0% |

（件数/金额含不同口径，占比按金额算；22 件里包含 3 件 0 元赠送，所以是 22 件对 291.01 元。）

也就是说：**吧台卖出去的东西，八成没挂到任何人头上。** 这不是系统丢数，是开单时没选销售人。
想让提成真正激励到人，得在收银流程里把「选销售人」做成必填动作；否则规则配得再好，
钱也发不出去。

**核对流程（三步，别只看一眼）**：

1. 销售总览按「销售人员」筛，`scripts/read-goods-sale.js` 会输出每人件数/金额；
2. 拿名字去 **员工管理**（`/staffManage/mgr`）对「姓名」列，确认岗位；
3. 隔天 8 点后看 **员工激励 → 提成结算**（`/staffManage/staffCommission/settlement`）
   的「未结算提成」有没有涨。**T+1 出数，当天对不出来是正常的。**

提成规则侧（四种算法、起征点、参与范围、可拆单套利）见 `references/13-员工激励.md`。

### 2.4 商品属性四选一（普通 / 自制 / 权益 / 网费）—— 建完就锁死

入口：销售管理 → 商超管理 → 商品管理 `shop/goods` → 顶部按钮「**商品入库**」。
弹窗标题「商品入库」，底部三个按钮：关闭 / 继续添加 / 添加。

「商品属性」下拉只有四项：**普通商品 / 自制商品 / 权益商品 / 网费**。
四种属性共有 商品分类、商品属性、商品名称、商品单位；每个属性再挂自己的一组字段。

| 属性 | 特有字段 | 适合什么 |
|---|---|---|
| 普通商品 | 商品条形码、商品标签 | 有包装、有条码的饮料零食 |
| 自制商品 | 商品标签 | 现制、无条码（茶水、简餐） |
| **权益商品** | **商品类型（服务/实物）、使用次数、有效期（月）** | **次卡、权益、服务类** |
| 网费 | 充值金额、赠送金额 | 与团购券同一套「本金 + 赠送」口径 |

三个字典项（商品分类 / 商品名称 / 商品单位）右侧都有 **「+ 添 加」**。
🔴 **2026-11-14 改版后已改为就地内嵌展开**，弹窗不关、已填内容不丢，
不用再「先跳去基础管理建好、再回来重填一遍」。四个面板的字段与校验见 §2.2.4。

> 🔴 **商品属性建完就改不了。** 保存后再点「编辑」，该项是
> `el-select__wrapper is-disabled` + `input.disabled = true`（2026-11-02 实测）。
> 选错只能删了重建，**而已经有销售单据的商品删不掉**。建之前先想清楚：
> 这东西是卖实物、卖现制、卖权益次数，还是卖网费。

#### 权益商品专章

1. **商品类型二选一：服务（默认）/ 实物。** 只有选「实物」才多出「商品条形码」。
   卖「洗浴 1 次」「台球 3 次」这类没实物的，保持「服务」。
2. **使用次数**：这份权益总共能用几次（不是每次几小时）。
3. **有效期**：填数字，后缀固定是「**月**」——`有效期 12 月` 就是一年，按自然月算，不是天。
4. **商品单位**建议选「**次**」（单位字典里已有 包/罐/盒/桶/**次**/个/杯/瓶/套/份/袋/块/条/张）。
5. **字段是分两批渲染的**：刚打开只有 7 项（分类 / 属性 / 类型 / 名称 / 单位 / 次数 / 有效期）；
   **选完「商品名称 + 商品单位」后整表重渲染成 14 项**，多出 允许网民自助购买 / 兑换所需积分 /
   进货价 / 销售价 / 销售时间 / 开启换购 / 允许会员网费购买。
   → 所以只读前 7 项就下结论会漏掉价格那一半（v1.6.16 第一版就漏了，v1.6.17 已修正）。

空表点「添加」的校验文案（实测，可当排错对照表）：

| 字段 | 报错 |
|---|---|
| 商品分类 | 请选择商品分类 |
| 商品名称 | **请选择商品**（不是"请选择商品名称"） |
| 商品单位 | 请选择单位 |
| 使用次数 | 请输入使用次数 |
| 有效期 | 请输入有效期 |
| 允许网民自助购买 | **请选择是否在客户端销售**（前 5 项填完才轮到它报） |

> ⚠️ **使用次数前端不校验数字**：实测输入 `abc` 能留在框里，「请输入使用次数」的提示还会消失，
> 只校验了"非空"。录入时自己盯住纯数字，别让脏数据进库。
> 商品名称是"下拉里选"而不是现打字（placeholder `请选择商品名称`，报错却说"请选择商品"），
> 打字不会过滤列表，也没有"创建"选项，新名字只能点右侧「添加」先建。

#### 2.4.1 实测走一遍：从零建一条权益商品

2026-11-02 在「南充测试」场所真实建了一条（`测试权益-洗浴1次`，服务类，1 次，12 月），全流程如下：

| 步 | 动作 | 实测结果 |
|---|---|---|
| 1 | 商品入库 → 「商品分类」旁「+ 添加」 | 弹「添加分类」（分类名称 / 排序 / 分类图片），确认后提示「操作成功」，**页面直接跳到 `baseManage/goodsCate?typeAdd=1`，入库弹窗一并关掉** |

| 4 | 填 分类=服务 / 属性=权益商品 / 类型=服务 / 名称 / 单位=次 | 选完名称+单位后弹窗从 7 项变 14 项 |

| 6 | 选 允许网民自助购买 = 是/否 | 不选直接报「请选择是否在客户端销售」。控件是 `el-radio-button`（不是 `el-radio`），按文字定位 |
| 7 | 点「添加」 | 弹窗关闭，列表「服务」分类下出现新行，库存三列与「兑换所需积分」都是 `--` |

**两个价格坑**：

- 🔴 **销售价是否落库，2026-11-14 改版后变了。**
  旧版本（2026-11-02 实测）在入库弹窗里输 `0.01`，提交后读回 `0.00`，必须回「编辑」重设。
  新版本实测（2026-11-14，商品 `测试入库品1114`）进货价 `0.01`、销售价 `0.01` **都存住了**。
  → 结论：新版入库可以直接定价，但**每次建完仍要回读 `salePrice`/`buyingPrice` 确认**，
  不要默认它一定存住，也不要默认它一定丢。
- **不填价 + 自助购买=是 = 0 元商品。** 入库不填价格时默认 `0.00`，

#### 2.4.2 🔴 商品名称必须带图片（图片挂在名称上，不在商品上）

**图片不是商品字段，是「商品名称」字典的字段。** 商品本身没有图片位，
商品管理列表第 3 列显示的那张图，就是名称字典里配的图。
**名称没图 = 这个商品在客户端/收银端永远是空白图。**

入口两条，效果一样：

- 商超管理 → 商品管理 → **基础管理** 页签 → 商品名称 `baseManage/goodsName`
- 商品入库弹窗里「商品名称」右侧「+ 添加」（会跳页，见上文）

「添加商品」弹窗只有两个字段：

| 字段 | 说明 |
|---|---|
| 商品名称 | 必填，placeholder `请输入商品名称`，**全局唯一** |
| **商品图片** | 上传卡片（`el-upload--picture-card`），提示原文「**图片格式为jpg、png、jpeg，图片大小不能超过500KB**」 |

上传细节（2026-11-02 实测）：

- 点 + 号选文件 → `POST https://c.51yunmeng.com/common-system/minio/upload` →
  返回 `{code:200, data:"https://upload.51yunmeng.com:9000/operation/BUSINESS_SHOP/<文件名>.png"}`
- 上传成功后 **+ 号消失**、显示 148×148 预览图（单图，一张定死）
- 列表「图片」列直接显示缩略图；名称字典里目前有图有无图混着（`茶水` 无图，`湘潭铺子槟榔` 有图）

🔴 **体积硬上限 500KB，超了是静默失败（铁律 #20）。**
选一张超过 500KB 的图，**弹窗里什么都不会发生**——不报错、不 toast、连「+」号都不变。
所以「传一张试试」试不出结论。上传前固定做一步：

```bash
python scripts/fit-image.py D:/img/咖啡.jpg --square --width 800
# → 输出 D:/img/upload/咖啡.jpg，实测字节数，目标 ≤480KB（留余量）
```

- 商品图位是**方图**（预览 148×148），源图不是方图就先 `--square` 居中裁，别让后台自己挤变形。
- 目标取 480KB 而不是 500KB：平台文案写「不能超过 500KB」，留 4% 余量防服务端重打包越界。
- 已达标（≤480KB 且 jpg/png/jpeg）就**原样传，不重编码**，别为了「统一处理」再压一遍掉画质。
- AI 生成图（ImageGen / 截图 / 拼图）动辄 1~4MB，**必须先过脚本再传**。

> 🔴 **图片只能在「添加」时传，编辑弹窗没有上传/替换/删除入口。**
> 实测编辑弹窗里只有 `el-image`（无图时显示「加载失败」），
> 既没有 `avatar-uploader`、也没有 `×` 删除按钮 → **建完就改不了**。
> 所以建名称的那一刻就要把图传上去，补不了。

两条约束，会拦住"事后补救"：

| 操作 | 结果 |
|---|---|
| 用同一个名字重新建 | ❌ 提示「**当前商品名称已存在，请勿重复添加**」（接口 code 500） |
| 名称已被商品引用时删除 | ❌ 提示「**请先删除:<名称>相关商品**」 |

**漏图之后唯一可行的补救顺序**（实测走通一遍，全程 4 步）：

1. 删掉引用该名称的**商品**（商品管理行内「删除」）
2. 删掉该**名称**（基础管理 → 商品名称 → 勾行 → 删除 → 确认）
3. 重新「添加商品」：**先传图**，再填名称，确认
4. 重新走商品入库，商品名称下拉选新建的这条

> ⚠️ 商品「编辑」里商品名称**可以改**（下拉，非禁用），所以不必删商品也能换名——
> 先建一条带图的新名称，再把商品的名称改指过去，最后删旧的空头名称。
> 唯一锁死的还是「商品属性」，别混淆。

### 2.5 套餐管理 `shop/goodsPackage`（组合销售，2026-11-02 实测）

套餐 = 把几个商品打包卖一个价。跟「团购套餐」（`groupManagement`，卖给美团/抖音的那种）**不是一回事**，
别混。这里的套餐走的是**吧台/客户端**渠道。

#### 2.5.1 列表

| 项 | 实测 |
|---|---|
| 路由 | `/marketManage/goodsManage/shop/goodsPackage`（三级；二级会回落） |
| 列（8） | 套餐名称 / 套餐类型 / 图片 / 单位 / 允许网民自助购买 / 兑换所需积分 / 销售价 / 操作 |

| 8 | 兑换所需积分 | input | 可空 |
| 9 | 销售价（元） | `input[type=number]` | ph `请输入套餐销售价` |

成功返回 `{code:200, data:"<套餐id>", message:"操作成功"}`。

#### 2.5.3 普通套餐 = 固定组合

「套餐内容」区点「选择商品」→ 二级弹窗「选择商品」：

- 列：商品分类 / 商品名称 / 商品单位 / 商品图片 / 操作，**每行一个「选 择」按钮**（不是勾选框）
- 顶部只有「商品名称」搜索框（ph 带空格：`请输入 商品名称`），按钮 `搜 索` / `清 空`
- 全店 41 条，10 条/页

点行内「选 择」→ 弹窗关闭，该行回填成 `商品名 更多 数量：[1]`。再点「添加商品」加下一行。

🔴 **行的顺序是倒序**：先选的排后面。实测选「生椰拿铁」再选「蒜薄块」，
回填显示 `蒜薄块 … 生椰拿铁 …`。不影响功能，但核对时别以为选错了。

#### 2.5.4 自选套餐 = 分类块 + 候选商品

切「自选套餐」后字段数从 10 变 8（原来的 2/3/4 合并成一个内容区），结构是：

```
[添加分类]                       ← 可加多个分类块
div.sort-item（一个分类块）
  分类名称：[ph 如饮料（3选1）]   可选数量：[2]
  1、 康师傅冰红茶  更多  数量：[1]  加购金额：[选填] 元
  2、 冰糖雪梨      更多  数量：[1]  加购金额：[选填] 元
  3、 茶π乌龙茶     更多  数量：[1]  加购金额：[选填] 元
  [+ 添加商品]                    ← 往本分类里加候选
```

含义：顾客从该分类里**任选 N 件**（N = 可选数量），套餐一个价；某个候选比别的贵时用「加购金额」补差价。
一个套餐可以挂多个分类块（实测现有「方便面自选套餐」就挂了 2 块）。

分类名称是**自由文本**，但本店习惯写成 `饮料（3选1）` 这种格式；实测填中文「饮料任选2件」也能正常落库。
选商品的弹窗与普通套餐**完全一样**（行内「选 择」、单选），所以两种类型可以共用一个 `pickGoods()` 封装。

#### 2.5.5 六个坑

**坑 1（最容易卡住）：「套餐图片」是必填，但标签上没有星号。**
不传图点提交，只报一行红字「**请上传套餐图片**」，字段列表里也看不出哪个是必填。
图片同样受 **≤500KB** 限制（铁律 #20），先用 `scripts/fit-image.py` 压。

**坑 2：底部「添 加」和「套餐单位」旁边的「添 加」同名。**
按文本 `^添加$` 找按钮会先命中**单位旁边**那个（新建单位），点了它什么都不发生，
表现是「提交了但没反应、弹窗还开着、没有 toast」。**必须限定在 `.el-dialog__footer` 里点。**

**坑 3：`el-select` 选中的值不写在 `input.value` 里。**
Element Plus 2.x 的 select 把显示值放在 `.el-select__placeholder` / `.el-select__selected-item`，
`input.el-select__input` 是 `is-hidden` 的 combobox、`value` 恒为 `""`。
→ 判断单位选没选，读那个 span 的文本、或看它有没有 `is-transparent` 类，**别读 input.value**。

**坑 4：「允许网民自助购买」是 `el-radio-button`，不是 `el-radio`。**
用 `.el-radio` 选择器会一个都找不到。判据是 `label.el-radio-button` + `.is-active`。
点法：找 `innerText` 精确等于「是」/「否」的 label，`label.click()`（原生点击会转发给内部 input）。

**坑 5：提交失败时前端只有兜底文案「现在系统繁忙，请再试一次。」**
看不出原因。必须同时截接口响应（`page.waitForResponse` 匹配 `goodsPackage` + POST），
才能拿到真实 code/message。**这条对全站写操作都适用。**

**坑 6：套餐图片上传成功与否，别用 `.el-upload img` 的可见性判据。**
缩略图会被 `offsetParent` 过滤掉，看起来像「没传」，实际已经传上去了
（列表有图、编辑回读 `img.src` 是 `https://upload.51yunmeng.com:9000/operation/BUSINESS_SHOP/xxx.jpg`）。
→ 稳妥做法：轮询 `dialog.querySelector('.el-upload img, .el-upload-list__thumbnail')` 的 `src` 是否以 http 开头，
或直接看提交是否报「请上传套餐图片」。

## 六、异常订单 `/marketManage/orderManagement`

### 6.1 页面与接口

| 页面 | 路由 | 按钮 |
|---|---|---|
| 未处理 | `/marketManage/orderManagement/pending` | 搜 索 / 清 空 / **已处理** / **退款** |
| 已处理 | `/marketManage/orderManagement/processed` | 查询类（无操作按钮） |

未处理列表列：订单来源 / 内容 / 充值金额 / 下单时间 / 姓名 / 证件号 / 操作。
已处理列表列：订单来源 / 内容 / 充值金额 / **充值时间** / 姓名 / 证件号 / **处理结果 / 处理人 / 处理时间**
（两页列名不同：未处理叫「下单时间」，已处理叫「充值时间」）。

两个 tab 共用**同一个接口**：

| 项 | 实测值 |
|---|---|
| 接口 | `POST /business-wy/recharge/getOperateRecord` |
| 请求体 | `{"param":"<RSA 密文>"}`，长度固定 **696 字符** |
| 响应 | **明文 JSON**：`{code, count, data[], message}` |
| 能否自建请求 | ❌ 不能，密文无法构造（同 §2.3，只能拦响应） |
| 场所范围 | **只含当前登录场所**，接口无场所入参，页面也无场所筛选 |

筛选只有三项：**下单时间 / 姓名 / 证件号**。没有场所、没有订单来源、没有处理状态。

### 6.2 🔴 两个 tab 返回同一批数据（已处理页是假的）

实测 2026-11-02，交替访问两页各刷新一次：

| 页面 | 请求体密文（前 12 字符） | 长度 | count | 返回 id | 记录 status |
|---|---|---|---|---|---|
| `pending` | `cUCfl5ijkGHu…` | 696 | 1 | `2113436440301056002` | **0** |
| `processed` | `0hKqNV6FBmE8…` | 696 | 1 | `2113436440301056002` | **0** |

**两页的请求体密文不同**（参数确实带了不同值，大概率是 status），**但返回的是完全相同的记录**，而且 `status=0`（未处理）。

后果，必须记住：

- **已处理页实际是 0 条**，却渲染出 1 行；该行「处理结果」为空、「处理人」为 `--`、`updateTime` 为 `""`。
  这正是「这条记录没被处理过」的证据。
- 报「已处理 N 条」之前，**必须数返回记录里 `status !== 0` 的条数**，不能看页面在哪个 tab、也不能信页面「共 N 条」。
- 已处理页的「共 1 条」是**同一批数据的重复计数**，不是独立统计。

> 判断真实归属只认 `status` 字段：`0` = 未处理。已处理值的编码本文未实测（见 §6.5）。

### 6.6 红线

**「退款」是真实资金动作，不可逆。** 点之前必须核对**三要素：姓名 + 证件号 + 金额**，并确认订单来源在可线上退款范围内。
看到「已处理」页有数据时先回头读 §6.2 —— 那大概率是同一条未处理记录。

实测现状（2026-11-02，南充测试场所）：未处理 1 条、已处理 0 条，总量就是 1 条。
若被要求「列出最近 5 条」，如实说明数据量不足，不要拆单充数。

## 七、典型流程

### 7.1 新品从零上架

1. 基础管理 → 商品分类：新建分类（名称 + 排序 + 图片）
2. 基础管理 → 商品名称：添加商品名称（**这里只填名称 + 图片，无价格**）
   🔴 **图片必须一起传**——图片挂在名称上，商品本身没有图片位；且名称建完就没有上传入口了（§2.4.2）
3. 基础管理 → 计量单位：确认单位存在
4. 基础管理 → 吧台设置：确认目标吧台
5. 商品管理 → 搜商品 → 补货（数量 = 入库数，上架吧台 = 出货到吧台数）
6. 商品管理 → 行内改「销售价 / 进货价 / 积分」
7. 基础管理 → 库存预警：设最低阈值

### 7.2 已有商品补货上吧台

见《08-补货上架.md》。核心：补货弹窗两个数量框含义不同，`数量` = 入库（加总库存），`上架吧台` = 从入库出货到吧台。

### 7.3 接团购单

1. 团购管理 → 团购套餐：建套餐（有效期 + 使用限制 + 单人核销次数）
2. 团购管理 → 上架管理：推到渠道
3. 核销管理 → 核销设置：确认收入统计口径
4. 日常：核销管理 → 核销记录 对账，异常订单 → 未处理 处理退款

## 八、红线

- **改库存有账**：所有库存变动都会写库存历史，写错只能反向调，删不掉。
- **补货 ≠ 上架**：两个数量框填成一样会导致总库存虚增（已踩过）。
- **核销口径只改一次**：改口径会让历史统计断层。
- **退款不可逆**：核对三要素后再点。
- **商品原价与促销价分开**：打折走商品促销，不要改主档销售价。

| 检查项 | 期望 |
