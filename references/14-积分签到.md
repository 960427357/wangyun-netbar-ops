# 14 · 积分签到（签到赠送）

> 数据基准：2026-10-31 实测，场所「演示门店」（placeCode 00000000000000）。
> 页面结构、字段语义、校验话术可跨店复用；**本店填的数值全是测试值，换店必须重填**。
>
> 这一页以前在 `06-营销配置.md` §3.2 只有一句话（「字段每日签到赠送」），
> 本次把三块（基础积分 / 签到活动 / 积分用途）全挖开了。**先读 §一 分清层次，再动手。**

---

## 一、先分清三个层次（最容易搞混的地方）

「积分签到」不是一个功能，是三层东西叠在一起，分别在不同页面：

| 层 | 在哪 | 干什么 | 谁给分/给奖 |
|---|---|---|---|
| ① 基础签到积分 | 签到赠送 → 签到活动设置 顶部 | 每天签到**送多少积分**（一个数字） | 只给**积分**，不给礼品 |
| ② 签到活动 | 同一个 tab 下半「活动列表」 | 连续/累计签到到第 N 天，**额外发礼品** | 礼包 / 专场卡 / 赠送网费 / 商品 |
| ③ 积分用途 | 积分设置 → **会员参与限制** | 积分能不能兑换商品、能不能参加活动 | 决定积分对顾客有没有意义 |

**关键：② 发的是礼品，不是积分；积分只由 ① 产生。**
想让顾客「签到攒积分换东西」只用 ① + ③；想「连续签 7 天送 30 元网费」才需要 ②。

> 🔴 **③ 是硬门槛，且必须三行全勾。** 只要这次要开签到活动、或者要让积分能兑东西，
> 就必须先在「会员参与限制」里把 `网吧会员积分`、`连锁会员积分`、`旺云签到积分`
> **三行都勾上「允许参与」**。三行缺一行，就会出现积分已经发出、顾客端却看不到的僵局。
> 细节与判据见 §6.2，顺序上这件事必须排在①和②**之前**。

另外，**积分是分钱包记账的**（见 §六），签到给的分记在「**活动赠送积分**」，
和充值送的「充值赠送积分」不是一个池子。

## 二、入口与页面骨架

**必须走菜单点进去。** 直接 `page.goto('/netBarActivity/scoreActivity/signIn/config')`
会被前端路由守卫重定向到 `/netBarSummary/handOver`（交接班页），看起来像「页面不存在」，
实际是没经过菜单。正确路径：

```
左侧图标栏 → 活动管理 → 顶部二级导航「积分活动」 → 直接落到「签到赠送」页
```

- 顶栏二级导航：整点抽奖 / **积分活动** / 游戏活动 / 商品促销 / 礼包设置（`.menu-box .menu-item`）
- 左侧子导航：`积分设置` / `签到赠送` / `转盘抽奖` / `积分记录`（`.left-menu-item`，
  注意不是 `.el-menu-item`，全页搜 `.el-menu` 会一个都搜不到）
- 签到赠送页两个 tab（真 `.el-tabs__item`）：
  `签到活动设置`(`…/signIn/config`) / `奖励发放记录`(`…/signIn/record`)

页面顶部有一行**版本门槛提示**，很多人忽略：

> 说明：**开启签到活动需将客户端升级至 9.5.7753.33 或更高版本**

也就是：后台配好了，网吧电脑上的旺旺宝客户端版本不够，顾客那边也签不了。
这是「配置没问题但没人能签到」的第一排查项。

## 三、基础签到积分（每日签到赠送）

签到活动设置 tab 顶部，一个数字框 + 一个「保 存」：

| 字段 | 控件 | 说明 |
|---|---|---|
| 每日签到赠送 | `input[type=number]` | 单位是「积分」，下方小字：用户每天成功签到可获得的基础积分 |

本店实测值 **10**（测试值）。这一项**独立于下面的活动列表**，只发积分不发礼。

**复核接口（明文，最可靠）**：

```
GET /business-wy/signConfig/getSignConfigByPlace
→ {"code":200,"data":{"id":"…","placeCode":"00000000000000","signDay":10,"status":""}}
```

`signDay` 就是「每日签到赠送」的积分数。`status` 本店为空串，语义未实测。

## 四、新建签到活动（`/netBar/addActivity?actType=signIn`）

**「新 增」不是弹窗，是新开一个配置页**（和转盘抽奖、充值赠送同一套容器）。

`/netBar/addActivity` 是**17 种营销活动共用**的容器，按 `actType` 分发组件：

```
lottery 转盘抽奖 / hours 整点抽奖 / promote 促销推广 / invitation 老带新活动
memberBirthday 会员生日活动 / recharge 充值赠送活动 / signIn 积分签到
LOL / pubg / delta / bladepoint（四款游戏战绩活动）
highRisk 高危人群 / riskGroup 风险人群 / highNetWroth 高净值人群
onlineCrowd 线上人群 / longTime 超时长人群 / salesDay 促销日
```

URL 参数：`?actType=xxx`；编辑 `&id=<活动id>&openType=edit`；只读查看 `&openType=view`
（view 模式下表单加 `.view-disabledForm`，底部按钮整块不渲染）。

> 这张表的价值：以前以为「促销人群」那五类（高危/风险/高净值/线上/超时长/促销日）
> 在别的模块，其实**全都挂在 addActivity 这个容器下**，只是页面没给入口按钮。

### 4.1 基础签到设置

| 字段 | 控件 | 约束（源码级） |
|---|---|---|
| 签到所需上机时长 | `el-input-number` | **0 ~ 24**，`step 0.5`，精度 1；0 = **不限制上机时长** |
| 活动策略启用时间 | `el-date-picker`（date） | 不能早于今天（disabledDate）；提交时补成 `YYYY-MM-DD 00:00:00` |
| 活动策略结束时间 | `el-date-picker`（date） | 必须 ≥ 启用时间；提交时补成 `YYYY-MM-DD 23:59:59` |
| 领取期限 | 单选 + 数字/日期 | 见下 |

**领取期限两种模式**（`giftDate`）：

- `1` = **发放日起 `[N]` 天内有效**（`giftpackLifespan`，默认 7，允许 1 ~ 99999）
- `0` = **指定日期区间**（`giftpackStart` / `giftpackEnd`，两个日期框）

校验话术（踩过才知道）：
`giftDate=1` 且天数为空 → 「请输入有效天数」；`giftDate=0` 且日期没选 → 「请选择日期」。

> 「上机时长」是这个功能的**防薅开关**：填 0，任何人在手机端也能签；
> 填 1 或 2，必须是**在店内上机满 N 小时**的会员才能签。默认值不填等于不设门槛。

### 4.2 签到模式

| 单选 | 内部值 | 页面文案 |
|---|---|---|
| **连续签到**（默认） | `attr = 0` | 连续签到：中断后，签到进度将重新计算。 |
| 累计签到 | `attr = 1` | 累计签到：活动周期内累计，中断签到不会清零。 |

档位表头会跟着变：连续模式显示「连续签到天数」，累计模式显示「累计签到天数」。

### 4.3 奖励档位

点「添加奖励」→ 弹 **`添加奖励` 对话框（800px，`.el-dialog`）**，不是行内编辑。

| 字段 | 约束（源码级） |
|---|---|
| 连续/累计签到天数 | `1 ~ 365`，整数；**不能超过活动周期天数**，否则报「请输入 1 至 365 天，且累计签到天数不能超过活动周期 N 天」 |
| 礼品内容 | 必填，四类任选：**礼品套餐（礼包）/ 专场卡 / 赠送网费 / 商品（最多 9 个）**；一个都不选 → 「请选择奖励」 |

对话框内两条规则：
- **天数重复** → toast「累计签到天数不能重复」
- 保存后**自动按天数升序重排**，不用自己排

礼品内容这四类的细节：

| 类型 | 说明 |
|---|---|
| 礼品套餐 | 弹「礼包套餐」列表，选的是**礼包设置里配好的礼包**（本店 3 个：免费上网5小时 / 到店赠送100元网费+红牛一杯 / 29.9元100 一杯饮品）。选中后会把礼包里的卡/商品/网费一次性铺进本档 |
| 专场卡 | 弹卡选择器，**只能选 1 张**；选了卡会**清空**网费金额 |
| 赠送网费 | 只有**赠送**网费一个数字框，**没有现金网费**（转盘抽奖那边有，这里被关掉了） |
| 商品 | 多选，**最多 9 个**，每个可填数量（1~99）；选择器会过滤掉网费类商品 |

> ⚠️ 奖励档位**不能发积分、也不能发抽奖次数**。想发抽奖次数只有「充值赠送活动」支持
> （`prizeType=4`）。这是产品边界，别再试。

页面上的两条硬约束（原文照抄，配之前一定要跟客户讲清楚）：

1. **最多配置 10 个奖励档位，相同签到天数不可重复。达到多个档位时逐档生成奖励，用户可分别领取。**
   → 签满 30 天，3/7/15/30 四个档位的奖励会**一起生成**，顾客逐档领。
2. **ⓘ 活动周期内，每个奖励档位仅可达成并领取 1 次；达到最高档后不再进入下一轮。**
   → 不是「每 30 天循环发一次」，是一个活动周期每个档只发一次。

### 4.4 保存

底部按钮 `保存提交` / `返回`（`scripts/create-signin.js` 默认只填不存）。
成功只弹 toast「**保存成功**」并自动返回列表，**没有二次确认**。

> ⚠️ **新增页会带出上次未保存的档位**（Vue keep-alive 保留状态）。所以 dry-run 一次之后再跑
> SAVE=true 的版本，页面里已经有 4 档，脚本再按同天数添加会逐个报「累计签到天数不能重复」——
> **这是正常现象，不是失败**。判断成功的标准看最后是否有 toast「保存成功」+ 回列表后档位数量正确。

### 4.5 保存 ≠ 生效：还必须打开「活动状态」开关

**这是最容易漏的一步。** 新建活动的 `status` 默认是 **0（关闭）**，列表里「活动状态」列是
`el-switch`，**默认处于关闭态**。不打开它，活动配得再对，顾客端也不会签到。

| 列表可见状态 | `status` | 操作列按钮 |
|---|---|---|
| 开关 off | `0` | **查看 / 编辑 / 删除** |
| 开关 on | `1` | **只有 查看** |

两个直接后果：

1. **保存后必须回列表把开关打开**（点 `.el-switch`，无二次确认、无 toast，`aria-checked` 变 `"true"` 即成功）。
2. **开着的时候改不了**——要改档位或日期，先关开关，操作列才会重新出现「编辑」。

> 这条和充值赠送活动的"停用后才出现编辑/删除"是同一套设计语言：
> **上线态只读，下架态可改**。做任何写操作前，先确认目标活动的开关状态。

## 五、payload 与复核接口

新增/编辑提交的体（读 `addSignIn-a9a755cc.js` 源码确认，不是猜的）：

```json
{
  "type": 18, "dataType": 0, "status": 0, "attr": 0,
  "limitTime": 0,
  "startTime": "2026-11-01 00:00:00",
  "endTime":   "2026-11-30 23:59:59",
  "giftDate": 1, "giftpackLifespan": 7,
  "prizeList": [
    {"name": "连续签到7天", "days": 7, "prizeType": 1,
     "activitiesPrizeRelationList": [
       {"prizeName": "赠送30元网费", "prizeType": 2, "prizeNum": 1, "gift": 30}
     ]}
  ]
}
```

- **`type: 18` = 积分签到**（顺带确认：`dataType: 3` = 转盘抽奖、`type: 9` = 充值赠送）
- `prizeType` 对照：`1` 商品 / `2` 网费 / `3` 专场卡 / `4` 赠送抽奖次数 / `0` 谢谢参与
- `activitiesPrizeRelationList`（注意是 **activities** 前缀）是**提交**用的奖品明细字段名；
  充值赠送活动那边叫 `prizeRelationList`。**两个名字容易抄错**。

> 🔴 **提交与返回不同名**（实测）：提交 payload 用 `activitiesPrizeRelationList`，
> 而列表/详情**返回**的是 `prizeRelationList`。所以用明文接口复核时，
> 按 `activitiesPrizeRelationList` 去取值会永远拿到空数组——不是没存上，是字段名不对。
> 正确取法：`data[].prizeList[].prizeRelationList[]`，其中 `gift` 是面值、`prizeType:2` 是网费、
> `prizeNum` 是份数。


**两个可直接复核的明文接口**（其余接口响应仍加密，别硬拼）：

| 用途 | 接口 | 关键字段 |
|---|---|---|
| 基础积分 | `GET /business-wy/signConfig/getSignConfigByPlace` | `signDay` |
| 签到活动列表 | `GET /business-wy/activitiesInfo/list?param=…` | 响应**明文**：`count` / `data[]`（`type`、`attr`、`limitTime`、`prizeList[]`） |

查询参数 `param` 是加密串，**不能自己拼**（拼了 406），只能截页面自己发的请求。

## 六、积分钱包：三类积分 + 两种来源

### 6.1 积分记录（`scoreActivity/exchangeLog`）

列：`会员名称 / 证件号 / 积分 / 操作(查看)`；筛选只有会员名称、证件号。
点「查看」弹 `积分详情`：

```
会员名称：xxx
充值赠送积分：0        ← 充值策略/充值活动给的
活动赠送积分：110      ← 抽奖、签到等营销活动给的
[积分消费] [获取记录]
消费项 / 积分 / 消费时间     例：积分清零、积分清零（本地转连锁）、兑换xxx 10分
```

**「充值赠送积分」和「活动赠送积分」分开记账**，签到产生的是后者。
所以「签到送的积分」在明细里不会和充值送的分混在一起，对账时按这两栏分。

### 6.2 会员参与限制（`scoreActivity/scoreSetting/Integral`）

这一页决定**积分对顾客到底有没有用**，是积分体系的真正总闸：

| 字段 | 控件 | 说明 |
|---|---|---|
| 积分兑换商品 | 单选 开启 / 关闭 | 关掉后积分不能换商品 |
| 权益卡是否允许非会员购买 | 单选 开启 / 关闭 | 与积分无关，但同页 |
| 网吧会员积分 | 两个复选：商超兑换商品 / 用户参加活动 | |
| 连锁会员积分 | 两个复选：同上 | |
| **旺云签到积分** | 两个复选：同上 | **签到积分单独一行**，可独立开关 |

页面原文说明（很重要）：

> 说明：当关闭**积分兑换商品**并且不允许用户使用**网吧会员积分、连锁会员积分、旺云签到积分**
> 参加活动后，在客户端将**不展示积分**。

联动规则（源码级）：三类积分里**任意一类**勾了「商超兑换商品」或「用户参加活动」，
「积分兑换商品」自动置为**开启**；三类**全部取消勾选**，则自动置为**关闭**。保存一次全部提交。

#### 🔴 6.2.1 三行必须全勾（客户明确要求，铁律 #22）

**只要本次要做这两件事之一，先来这里把三行配齐：**

- 要开**积分签到活动**（签到发积分、发礼品）；
- 要开**积分兑换**（积分换商品、积分换网费）。

**要求：`网吧会员积分`、`连锁会员积分`、`旺云签到积分` 三行都要有勾选，不允许留空行。**
每行有「商超兑换商品」「用户参加活动」两个复选，按本次的业务用途决定勾哪几个，
但**三行都不能是空**，这是硬性下限。

| 行 | 要兑换商品时 | 要参加活动（签到/抽奖）时 |
|---|---|---|
| 网吧会员积分 | 勾「商超兑换商品」 | 勾「用户参加活动」 |
| 连锁会员积分 | 勾「商超兑换商品」 | 勾「用户参加活动」 |
| **旺云签到积分** | 勾「商超兑换商品」 | 勾「用户参加活动」← 签到活动靠这个 |

**为什么不能只勾一行。** 页面原文的意思是：三类积分**都不允许**参加活动时，客户端**不展示积分**。
反过来说，只要有任意一类被允许，页面就认为体系在跑，但顾客手里真正持有的积分可能属于另一类钱包
（§六：签到分记「活动赠送积分」，充值分记「充值赠送积分」）。只勾了 A 类、顾客攒的是 B 类，
顾客端就是看不到、用不了。看起来一切都配了，实际是一个半死的状态。

**最容易踩的误判**：勾了任意一类之后，页面上方那个 `积分兑换商品` 就自动变成「开启」。
很多人看到总开关是开的，就以为已经配好了，回头去查「为什么顾客端没积分」。
**总开关自动开启只证明你勾过至少一行，不证明三行都勾了。**

**顺序要求**：这一步放在建签到活动、配兑换商品**之前**。事后补勾，补之前那几天签到的会员
虽然拿到了分，但顾客端看不到入口，等于白签（分数还留在账上，解释起来很麻烦）。

> 首次进这页如果显示的是一个「**积分同步**」按钮而不是开关，说明该场所**积分体系还没初始化**，
> 必须先点「积分同步」才能配。本店已初始化，所以直接看到开关。

### 6.3 积分等级（`scoreActivity/scoreSetting/grade`）

`等级设置` tab：列 `等级名称 / 等级 / 所需积分 / 创建时间`，可「新 增」。
这是**积分等级**，和计费那边的「会员等级」是两套体系，名字像、不相干（见 `03-计费与会员.md`）。

## 八、和「抽奖 / 充值」体系的衔接现状（本店）

这三件事很容易被混成一个「积分闭环」，实际是三条并行、**互不连通**的路：

| 想要 | 现实 |
|---|---|
| 签到攒积分 → 用积分抽转盘 | ❌ 走不通。转盘的「积分参与次数上限」已被设成 **0**（关掉积分抽奖，只认赠送次数，见 `06-营销配置.md` §3.2） |
| 签到 → 送抽奖次数 | ❌ 产品不支持。签到档位只有 礼包/专场卡/网费/商品 四类，`prizeType=4` 只存在于充值赠送 |
| 签到积分 → 换商品 | ✅ 可以，但「会员参与限制」里三行都要勾（§6.2.1），`旺云签到积分` 那行还得勾「商超兑换商品」 |
| 签到 → 送网费/商品 | ✅ 直接配档位，注意这是**真实成本** |

**结论口径（对客户就这么说）**：签到负责「每天来一次」，抽奖次数由**充值**驱动，
两条线目前是分开的；签到送的积分只能换商品，不能拿来抽奖。

## 九、成本与门槛（只讲结构，不报本店数字）

签到是**持续小额支出**，配之前先算三笔：

1. **基础积分成本** = 每日签到赠送积分 × 日均签到人数 × 天数 ÷ 兑换率
   （积分本身不是钱，能换商品才是钱 → 看「积分兑换商品」开不开、换什么）
2. **档位奖励成本** = 每档礼品价值 × 达到该档的人数（连续签到档位天然筛掉大部分人）
3. **门槛决定漏损**：`签到所需上机时长 = 0` 时，顾客在家用手机就能签，
   成本按「全体会员」放大；设成 1~2 小时，成本立刻收敛到「到店客人」

结构层面的两个「别这么配」：

- ❌ 只配 1 个低档位（签到 1 天送 5 元网费）→ 等于无门槛发钱
- ❌ 一档塞满礼包 + 商品 + 网费 → 单档成本失控，且顾客看不出价值

## 十一、坑清单

1. **直连 URL 会被踢到交接班页**（`/netBarSummary/handOver`），必须走菜单点。全站只有少数页能直接 goto。
2. **「新 增」是独立页不是弹窗**（`/netBar/addActivity?actType=signIn`），抓 `.el-dialog` 会抓空。
3. **日期必须最后填**：中途改一次「签到模式」单选会重渲染，把已填日期清空（同提成规则的坑）。
4. **日期框带 readonly**：直接 `fill` 无效，要 `removeAttribute('readonly')` 再写值；收起面板点空白处，
   **不要按 Esc**。
5. **奖励天数不能超过活动周期**：30 天活动里配「签到 45 天」直接被拦，报错文案见 §4.3。
6. **赠送网费填 0 等于没填**：0 会被清空，保存时报「请选择奖励」。要么填正数，要么换成别的礼品类型。
7. **同一档位天数不能重复**，且保存后自动按天数升序，别以为自己填乱了。
8. **保存成功只有一句「保存成功」**，没有二次确认、页面上也看不到活动 id，回列表核对最快。
9. **客户端版本 ≥ 9.5.7753.33**，否则顾客端签不了——这是「配了但没人签到」的第一嫌疑。
10. **在列表页搜 `.el-menu` 找不到左导航**，类名是 `.left-menu-item`（原生 div，不是 Element 菜单）。
11. **保存成功 ≠ 活动生效**：新建后「活动状态」开关默认关闭，要手动打开（§4.5）。这是最贵的坑——
    配完以为上线了，其实一条都没跑。
12. **开启状态下编辑/删除按钮消失**，只剩「查看」。改配置前先关开关。
13. **重复跑脚本会报「累计签到天数不能重复」**：新增页会保留上次未保存的档位，
    脚本按同天数再加就被拦。看最后有无「保存成功」toast 判断，别被中间报错吓到。
14. **明文复核时奖品字段名是 `prizeRelationList` 不是 `activitiesPrizeRelationList`**（§五）。

## 十三、运营设计：用它拉活跃度、留人（不是配置，是设计）

> 客户问的从来不是「怎么配」，而是「怎么配才有用」。下面五条是从产品结构反推出来的设计原则，
> **与填多大数字无关，换店也成立**。具体档位面值要按本店客单价重算。

### 13.1 周期 = 刷新频率，这是第一个决策

因为「每档每周期只发一次、达到最高档后不进下一轮」（§4.3），**活动周期就是这套玩法的刷新节奏**：

| 周期设成 | 实际效果 |
|---|---|
| 一周 | 周任务。适合高频网吧，老客每周都有新目标 |
| **自然月**（推荐常态） | 月任务。节奏与「月度消费」对齐，成本好核算 |
| 半年 / 一年 | ❌ **第二个月起活动就死了**，没人能再拿奖。最常见的配错 |

**推论：周期用完必须手动重建。** 把「每月 1 日重建签到活动」写成固定运营动作，否则月初会出现"零活动"空窗。

### 13.2 主活动用「累计」，别用「连续」

这条最反直觉，也最影响结果。

| | 连续签到（attr=0） | 累计签到（attr=1） |
|---|---|---|
| 断一天 | 进度清零 | 不清零 |
| 实际筛出谁 | 本来就天天来的核心钉子户 | 每周来 2~3 次的中腰部 |
| 对活跃度的边际拉动 | 很弱 | **很强** |
| 成本刚性 | 高（钱发给最不需要激励的人） | 中 |

**要提活跃度 → 累计。** 连续签到只适合「7 天周期 + 一瓶饮料」这种小额彩蛋，
**不能**配「连续 30 天送 60 元」，那等于第一天就劝退 95% 的人。

### 13.3 上机时长是唯一的成本闸门

`limitTime` 是这套功能里唯一能区分「到店签到」和「居家签到」的字段：

- `0` → 全体会员在家点手机就能签，成本按**全量会员**放大，且零到店转化
- `1` → 只覆盖"开机坐一会儿"的人，是性价比最高的档位
- `2` 以上 → 会误伤短时客，只在预算极紧时用

> 待验证：`limitTime` 是**活动层**字段，`signConfig` 里没有。所以「每日签到赠送积分」是否也受这个门槛约束，
> 目前不确定。若不受约束，居家签到仍能攒分 —— 但积分只能在店内兑换（§6.2），等于"预约到店"，损失可控。
> 想彻底封死就把 `signDay` 调低。

### 13.4 档位排布：低档给商品，高档给网费

- **第 1 档（最易达成）→ 商品**（矿泉水/可乐/零食）。即时兑现、当场拿到、感知最强，成本 2~4 元；
  而且把"签到"和"到吧台"绑在一起，员工有推销机会。
- **中档 → 赠送网费**。延迟消费，是"下次再来"的钩子，成本递延到下一次上机。
- **最高档 → 网费 + 小食组合**。能拿到的人少，面值可以放大。

反过来（第 1 档直接送网费）就是无门槛发钱。

**必须提前接受的产品行为**：多档达标时奖励**逐档一次性生成**，签满 22 天会在同一天看到
5+15+30+60 四份奖励堆在一起。所以：① 档位面值要排得缓（别 5/50/200）；② 成本会在月末集中兑现；
③ 把第 1 档换成商品，让"第一次拿到东西"发生在第 5 天而不是第 22 天。

### 13.5 成本与验证

```
网费成本 ≈ Σ（各档面值 × 达到该档及以上人数）
现金等价 ≈ 网费成本 × 核销率(60%~80%)
积分成本 = signDay × 30 × 活跃会员数 ÷ 兑换比例 × 兑换核销率
```

按每 100 名活跃会员、4 档 5/15/30/60、达成率 30%/20%/12%/8% 估算：
**≈2,030 元网费 ≈ 1,420 元现金等价，人均约 14 元/月**，加积分层约 18~20 元/人/月。
回本线：签到让会员**多来 1 次**即打平。

**只看三个指标**：

1. **签到渗透率** = 当日签到人数 ÷ 当日上机会员数（≥30%）
2. **档位达成分布**（第 1 档 ≥40%，最高档 5%~10%）
3. **到店频次增量** = 签到会员月均到店天数 − 非签到会员（≥ +1 天）。**只有这个能证明留存真的提升**

前两个在「奖励发放记录」看，第三个要导会员消费明细分组对比。

### 13.6 上线前置（漏一条就白配）

1. **会员参与限制三行全勾**（§6.2.1）—— `网吧会员积分` / `连锁会员积分` / `旺云签到积分`
   都要有勾选。三行缺一行，顾客端不展示积分，后面几条全白做。**这一步排在第一位。**
2. **配积分兑换商品** —— 兑换池空的，`signDay` 就是废纸，签两天就没人签了
3. **客户端 ≥ 9.5.7753.33**（§二）
4. **员工口头提醒 + 收银台提示物** —— 签到这动作不提醒等于没有
5. 顾客端入口位置**必须在店内实机确认**，后台看不到

一键落地：`scripts/create-signin.js` 默认 CFG 已是本节的「稳健方案」（1h / 累计 / 5-10-15-22 天 → 5-15-30-60 元）。
