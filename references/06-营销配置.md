# 旺云商户端 · 营销配置技能手册 v1（会员促销 + 活动管理）

> 路由前缀 `/memberActivityManage`、`/netBarActivity`，门店「演示门店」。
> 状态：2026-10-29 实测，弹窗字段为实际打开「新增」抓取，未提交任何数据。
> 用途：拉新、唤回、券、充值赠送、抽奖、签到、礼包。

---

## 一、结论先行

1. 营销分两大块：**会员促销**（按人群圈人、发券、充值赠送）和**活动管理**（抽奖、签到、游戏、礼包、商品促销）。
2. 促销的核心是「**先定人群，再配策略**」。人群是名单，策略是给这群人什么价。名单为空时策略不会触发，这是「配了没效果」的第一原因。
3. 券和礼包最容易踩的坑是**有效期**：券有「天数 / 固定日期」两种，礼包有「有效期」字段，选错就成永久券。
4. 商品促销的折扣作用在商超商品上，和区域计费无关，别混为一谈。

### 2.1 八类人群（促销人群）`/memberActivityManage/promotion/*`

路径：左侧 **会员促销** → 二级 **促销人群**，默认落在「流失预警」。8 类人群的切换入口在**页内左侧**
（`div`，不是 `el-menu-item`，用 `li` 选择器找不到）。

🔴 **名单不是实时算的。** 规则改完不会马上出现在名单里，要等到**周一**跑一次统计才落到名单上
（客户口径，未实测跨周）。所以「改完规则名单没变化」是正常现象，别急着怀疑配置写错；
名单为空时先回 §2.2 核对阈值，再确认是不是还没到统计日。

| 人群 | 路由 | 表格列 | 本店现状 |
|---|---|---|---|
| 流失预警 | `/promotion/churnWarning` | 姓名 / 手机号 / 上网频率 / 最后到店 / 流失天数 / 策略名称 / 策略状态 / 领取状态 / 发券历史 / 操作 | 0 条 |
| 高净值人群 | `/promotion/highNetWorth` | 姓名 / 手机号 / 策略名称 / 策略状态 / 领取状态 / 发券历史 / 操作 | 2 人 |
| 线上人群 | `/promotion/onlineCrowd` | 姓名 / 手机号 / **首次注册** / 策略名称 / 策略状态 / 领取状态 / 发券历史 / 操作 | 0 条 |
| 上机超时长人群 | `/promotion/onlineOverTime` | 姓名 / 手机号 / 策略名称 / 策略状态 / 领取状态 / 发券历史 / 操作 | 0 条 |
| 会员生日 | `/promotion/memberBirthday` | 姓名 / 证件号 / 发送时间 / 策略名称 / 礼品内容 / 状态 | 0 条 |

| 老带新 | `/promotion/invitation` | 策略名称 / 老会员 / 老会员赠送 / 新会员 / 新会员赠送 / 创建时间 | 2 条 |
| 不参加人群 | `/promotion/notParticipate` | 姓名 / 手机号 / 最后到店 / 促销次数 / 操作 | 1 人 |

页面之间的结构差异（照着统一模板抓会抓错）：

- **「流失预警」页内还有 3 个 tab**：`全部预警 / 高危人群 / 风险人群` —— 它是把风险与高危合在一个名单里看。
- **生日、促销日两页没有「操作」列**，是只读流水（礼品内容 / 状态），不能在这里补发。
- **老带新是成对流水**（老会员 + 新会员 + 各自赠送），不显示手机号，身份证掩码成 `5116************98`。
- **「不参加人群」只有「删除」**，没有"加入"按钮；一旦在里面，就收不到任何促销（含生日礼）。
- 其他人群的「操作」列是「不参加」按钮 —— 点它等于把这个人拉进排除名单，**这是写操作**。

指标条：流失预警 / 高净值 / 线上 / 上机超长 / 生日 / 促销日 六页顶部有
`总人数 / 已领取 / 未领取 / 促销成本`；老带新页只有 `促销成本`；不参加人群**没有指标条**。

接口（前缀 `/business-wy/promotionCrowd/`，全部 POST，响应明文 JSON）：

|---|---|

| 线上人群 | `online` |
| 高净值 | `crowdPromotionResult` |

### 2.2 规则设置 `/memberActivityManage/baseConfig/rules`

> ⚠️ 旧版本节写的「一组开关 + 周一~周日复选，决定每个活跃人群在哪些星期被判为活跃」**是错的**。
> 周一到周日的复选**只属于「上机超长人群」的高峰日期**，不是所有人的统计日。以本节为准。

三项全局：

| 项 | 本店值 | 作用 |
|---|---|---|
| 是否启用会员促销 | 开 | 总闸，关掉整个模块不跑 |
| 周上机频率 | 过去 4 周（28天）/ 总上机次数 **30** | 下面所有"几倍"的基数 |
| 自动营销策略（同一会员同一类型） | **4** 天内仅触发一次 | 防同一个人被反复发券 |

六类人群的判定公式（页面原文 + 本店实测值）：

| 人群 | 页面原文 | 本店值 |
|---|---|---|
| 高危 | 1、间隔天数超过周上机频率的 [4] 倍，且现金余额 ≤ [10] 元 | 4 倍 / ≤10 元 |
| | 2、间隔天数超过周上机频率的 [5] 倍，即使现金余额 > [20] 元 | 5 倍 / >20 元 |
| | 3、会员超过 [28] 天未上机时，直接归为高危 | 28 天 |
| 风险 | 1、超过周上机频率的 [2] 倍，且现金余额 ≤ [10] 元 | 2 倍 / ≤10 元 |
| | 2、超过周上机频率的 [3] 倍，且现金余额 ≤ [20] 元 | 3 倍 / ≤20 元 |
| 休眠 | 1、会员超过 [180] 天未上机时，直接归为休眠 | 180 天 |
| 线上 | 1、首次注册后的 [14] 天内，未发生充值时保持线上人群身份 | 14 天 |
| 高净值 | 1、充值金额排名前 [30] 的会员 | 前 30 |
| | 2、消费金额排名前 [30] 的会员 | 前 30 |
| 上机超长 | 1、高峰日期：周一~周日复选 | **周五 + 周六** |
| | 2、高峰时段 [16:00] 至 [22:00] | 16:00–22:00 |
| | 3、高峰日期和时段内，单次上机时长超过 [4] 小时 | 4 小时 |

**读值要点**：这一页**没有标准 `el-form-item` 包裹**，数字输入框是内联在句子里的普通 `input`，
`innerText` 读出来数字位置是空的（`超过周上机频率的 倍`）。按 form-item 拆块会全部错位。
正确做法是按 DOM 顺序把「该输入框之前的文字」与 `input.value` 配对：

```js
// 文本节点累积 pending，遇到可见 input 就输出 {before: pending.slice(-50), value}
```

**接口（🔴 保存是 GET，不是 POST）**：

```
GET /business-merchant/crowdRule/query              读，明文 JSON
GET /business-merchant/crowdRule/save?param=<RSA>   写 → toast「保存成功」
```

`query` 返回字段与本店值：

| 字段 | 值 | 对应页面 |
|---|---|---|
| `enabled` | 1 | 是否启用会员促销 |
| `highRiskMultiplier` / `highRiskXy` | 4.0 / 10.0 | 高危① 倍数 / 余额 |
| `highRiskMultiplierHigh` / `highRiskXyHigh` | 5.0 / 20.0 | 高危② 倍数 / 余额 |
| `directHighRiskDays` | 28 | 高危③ 直接判高危天数 |
| `riskMultiplier` / `riskXy` | 2.0 / 10.0 | 风险① |
| `riskMultiplierHigh` / `riskXyHigh` | 3.0 / 20.0 | 风险② |
| `dormantDays` | 180 | 休眠 |
| `onlineIdentityValidDays` | 14 | 线上 |
| `highValueRechargeTopN` / `highValueConsumeTopN` | 30 / 30 | 高净值两项 |
| `longSessionPeakDays` | `"5,6"` | 高峰日期（1=周一 … 7=周日） |
| `longSessionPeakHoursS` / `longSessionPeakHoursE` | 16:00 / 22:00 | 高峰时段 |
| `longSessionDurationHour` | 4.0 | 单次时长阈值 |
| `autoSendCouponDays` | 30 | ⚠️ 语义存疑，见下 |

⚠️ **有两个数字对不上，别照着字段名猜**：
- 页面「总上机次数」填 30，但 `query` 里没有独立的"周上机频率"字段，最接近的只有 `autoSendCouponDays=30`；
- 页面「同一类型 4 天内仅触发一次」，`query` 里**没有任何等于 4 的字段**。

这两项要么共用字段、要么前端展示值并不来自本接口。**要改这两项，先存一次再 `query` 比对**，
不要假设 `autoSendCouponDays` 就是"周上机次数"。未验证。

### 2.3 策略设置 `/memberActivityManage/strategy/*`

左侧 8 类（**没有「流失预警」也没有「不参加人群」**）：
风险人群 / 高危人群 / 高净值人群 / 线上人群 / 上机超时长人群 / 促销日 / 会员生日 / 老带新。

> 「促销人群」里的「流失预警」= 这里的「风险 + 高危」合并视图，同一批数据的两种看法。

两 tab：**当前策略 / 历史策略**（当前可改，历史只读留痕）。
列表列：活动名称 / 礼包内容 / 预估成本 / 活动时间 / 创建时间 / 状态 / 属性 / 操作。

「添 加」**不是弹窗**，跳独立页 `/netBar/addMemberActivity?actType=<人群>`。
🔴 **actType 和列表路由不是一套命名，而且点进去的表单模板还不一样**（2026-11-03 逐页实测）：

| 人群 | 列表路由 | 添加页 actType | 表单模板 |
|---|---|---|---|
| 风险人群 | `/strategy/riskGroup/list` | `riskGroup` | 券型 |
| 高危人群 | `/strategy/highRisk/list` | `highRisk` | 券型 |
| 高净值人群 | `/strategy/highNetWroth/list` | `highNetWroth`（**Wroth 是拼错的，但路由就是这个**） | 券型 |
| 线上人群 | `/strategy/onlineCrowd/list` | `onlineCrowd` | 券型 |
| 上机超时长人群 | `/strategy/computerLongTime/list` | **`longTime`** | 券型 |
| 促销日 | `/strategy/salesDay/list` | `salesDay` | 券型 **+ 适用会员等级** |
| 会员生日 | `/strategy/memberBirthday/**birthday**` | `memberBirthday` | **礼包型** |
| 老带新 | `/strategy/invitation/list` | — | — |

- 上机超时长列表叫 `computerLongTime`，添加页却是 `longTime`；用错的 actType 打开是**空白页**
  （没有表单、没有报错），只会卡在等 `input[placeholder="请输入活动名称"]`。
- 会员生日的列表路由是 `/birthday` 不是 `/list`，访问 `/list` 直接「您的权限可能变更，找不到当前页面」。

**两种表单模板**（照着券型模板去抓会员生日会全线错位）：

| | 券型（6 类） | 礼包型（会员生日） |
|---|---|---|
| 名称 | 策略名称（50 字） | 活动名称（50 字） |
| 有效期 | 无（用券有效期天数表达） | 单选 **长久有效（默认）/ 时间范围** |
| 会员等级 | 只有促销日有 | **有，必勾** |
| 礼包设置 | 有 | 有 |
| 活动开放规则 / 券有效期 / 属性 / 发送渠道 / 促销文案 | 有 | **全都没有** |

礼包型的礼物是系统按生日自动推的，所以没有渠道和文案字段。

### 礼包套餐弹窗（必看）

🔴 **「礼包套餐」弹窗打开是空的（暂无数据），必须点一次「搜 索」才会加载**：

`POST /business-wy/activityGiftpack/list`。不点就以为"本店没有礼包"，直接卡在这一步 ——
和列表页"改了查询条件要点搜索才生效"是同一个毛病（铁律 #14）。本店实际有 5 条。

实测反复打开后它也可能直接带出 5 行（有缓存）；**判据不是"有没有行"，而是"目标礼包在不在列表里"**，
所以按名称搜一次、再按名称匹配行更稳。

**礼包从哪来**：`活动管理 → 礼包设置` `/netBarActivity/giftPackage`
（列：礼包名称 / 礼包内容 / 预估成本 / 创建时间 / 操作）。
**没有礼包就建不成策略** —— 这是"想做会员促销但做不出来"的第一原因。

本店 5 条礼包（2026-11-03 实测）：

| 礼包名称 | 礼包内容 | 预估成本 |
|---|---|---|
| 测试-只送网费30加红牛 | 30元赠送网费， 红牛*1 | 10 |
| 测试-包时卡加网费 | 5小时包时 | 20 |

礼包内容的三种口径（对应 §3.5 的 `prizeType`）：
`赠送网费`（金额，prizeType=2）/ `专场卡`（包时，prizeType=3）/ `商品`（红牛等，prizeType=1）。

> 「测试-包时卡加网费」和「免费上网5小时」的礼包内容**都是 `5小时包时`**，
> 光看内容分辨不出来，只能靠**礼包名称**选。选完必须回读「礼包设置」那行核对，

| 发送渠道 | 复选 旺旺宝网吧版APP / 公众号 / 短信 | **默认一个都不勾**，不勾等于不发 |
| **促销文案** | 每勾一个渠道就多出一个**必填**输入框（maxlength 200，带 `0 / 200` 计数） | 见下 |

🔴 **「促销文案」是页面内联出现的必填项，不是基础设置里的那条**：
勾上「旺旺宝网吧版APP」后，同一行里立刻插入一个 `el-autocomplete`
（placeholder =「促销文案可用于发送通知(可选择配置的也可直接输入)」）。
不填就提交 → toast 只给一句「**请检查是否填写完整**」，页面上找不到任何红字，
按「必填」去找也找不到（它没有独立的 form-item label 星号）。实测两个渠道只出一个输入框（共用一条文案）。

> 它的作用 = **这条促销消息发给网民时给顾客看的正文**（微信服务号 / 旺旺宝网吧版推送），
> 和「基础设置 → 宣传文案」里那套通用文案是两码事：这里是**按策略写**的。
> 金额、时长必须和礼包内容逐字一致，否则顾客拿着消息来对账。

🔴 **「开启活动」在表单里显示关，存进去却是开的**：
表单开关 `was=false`，不去动它直接提交，列表「状态」列照样是**开**、操作列只有「查看」。
所以不能拿表单开关当依据，**以列表状态列为准**；要真关掉只能回列表点那一列的开关。

### 礼包型的字段

活动名称 / 有效期（长久有效 · 时间范围）/ 开启活动 / 适用会员等级 / 礼包设置。
没有渠道、没有促销文案、没有券有效期 —— 生日礼由系统到期自动发。

### 列表状态开关与操作列

「状态」是 `el-switch`，点一下立刻切换、**无二次确认**，toast「操作成功」。

- 开关**开** → 操作列只有「查看」
- 开关**关** → 操作列变成「查看 编辑 删除」（编辑是 `&openType=edit`，删除弹「确定将选择数据删除?」再确认，toast「删除成功」）

所以「想改某条策略」的正确路径永远是：**先去列表把它停用 → 出现「编辑」→ 再改 → 改完重新打开**。

### 提交与生效（实测）

- 提交按钮「保存提交」→ `POST /business-wy/activitiesInfo/add`（新增和编辑都走这个，实测新增返回后直接跳回列表）
- **失败时只有 toast，没有字段级提示**；常见两句：
  - 「请检查是否填写完整」= 礼包没选 / 促销文案没填 / 会员等级没勾
  - 「选择的时间段内已经有活动了！」= 同一人群同一天已经有一条「每日」策略在跑
- **建完立刻生效，不需要等周一**：`促销历史 → 进行中` 马上就有这一条。

### 2.5 充值赠送活动 `/memberActivityManage/rechargeGift`

列表列：活动名称 / 有效期 / 礼品内容 / 状态 / 创建时间 / 操作。筛选：活动名称、状态。按钮：搜 索 / 清 空 / 添 加。
列表可以有多条并存，每条各自有独立的状态开关。

与 `/msBarOptions/deposit`（充值活动方案，只读，列 充值金额/赠送金额/允许修改金额/描述）**不是一回事**：

- `deposit` = 计费侧的固定充值档位，收银台直接用。
- `rechargeGift` = 营销侧的限时活动，可带礼品、有有效期。

两处都有赠送时，先确认是否叠加，避免充 100 送 30 + 活动再送 30。
再叠加 `09-门店资料` §3.2 的「充值策略」（充X送Y 元），一共三处会给钱，配第二个之前先算总赠送率。

> 🔴 **充值赠送活动送不了「网费金额」**（2026-11-02 复核）：这个页面的奖品只有
> 抽奖次数 / 专场卡 / 商品 三类，**没有「充 100 送 50 元」这种纯金额入口**。
> 纯金额赠送只在 `deposit` 那一页，而那一页本账号显示
> **「当前版本无法修改充值活动方案」**，只有「刷新」按钮、只有一条 `充[0元]送[0元]`，
> 5 个分类（临时用户 / 专场用户 / 会员用户 / 连锁会员 / 会员日活动）全都改不了。
> 会员日活动那栏同样只读：已配 每月固定 1 日 + 特定日期 2026-06-05、2026-06-10（本地会员），
> 选项「开启会员日优惠充值方案功能」「新办会员享受会员日优惠充值1次」也点不动。
> **客户要「充多少送多少」，先让他确认这是不是版本没开**，别在这里找配置项。
> 退路：用「专场卡」表达送时长（送 2 小时 = 送 12 元网费），或用商品赠品送实物/服务。

#### ★ 状态开关 + 操作按钮的隐藏规则（2026-10-31 实测）

「状态」列是 **`el-switch` 开关**，点一下立刻切换、**无二次确认**，成功 toast「操作成功」。

**活动启用（开关 on）时，操作列只有「查看」；把开关关掉、活动停用之后，「编辑 / 删除」才出现。**
所以「想改某条活动」的正确路径是：**先停用 → 操作列变成「查看 编辑 删除」→ 再编辑**。
别看到只有「查看」就以为这页不支持修改（旧版本这里就是这么误记的）。

#### 「添 加」是跳独立页，不是弹窗

`/netBar/addMemberActivity?actType=recharge`；查看详情是同一页带 `&id=<活动id>&openType=view`（只读），
编辑是 `&id=<活动id>&openType=edit`（回填完整，见下文实测）。

**保存成功后不弹 toast，而且跳转目标不固定**：
2026-10-31 那次回到列表页，2026-11-02 这次直接落到 `/netBarActivity/hoursActivity`（活动管理-整点抽奖，
就是浏览器历史里的上一页）。**不要靠跳转判断成败** —— 保存后一律手动 `goto`
`/memberActivityManage/rechargeGift`，读第一行核对名称/礼品内容/开关状态。

表单字段（按页面顺序）：

| 字段 | 控件 | 说明 |
|---|---|---|
| 活动名称 | 文本，最长 50 | |
| 有效期 | 单选：**长久有效（默认） / 时间范围** | 选「时间范围」后要填起止 |
| 开启活动 | 开关，**默认关** | 不打开则不生效 |

#### 奖品档位：「充值满 X 元，赠送抽奖 N 次」

每档是 `.prizeItemBorder`，文案固定为「充值满 `[cash]` 元 ，赠送抽奖 `[n]` 次」，
块内就是两个 `input[type=number]`：**第 1 个 = 充值门槛（元），第 2 个 = 赠送抽奖次数**。

一档除了抽奖次数，还能**同时**挂另外两类奖品（三者不互斥，2026-11-02 实测叠加保存成功）：
- **赠送专场卡**（「选择专场卡」）
- **商品**（「选择商品」，最多 9 个）

按钮：「添加规则」增加一档（**最多 6 档**，到 6 档后按钮直接**不渲染**、不是置灰）；
「移动」拖动排序；**单档时块内没有「删除」按钮，加到 2 档后每块才出现「删除」**。

#### 三类奖品的挂法（2026-11-02 实测细节）

**① 赠送抽奖 N 次** — 就是档位里那个数，依赖「活动管理 → 整点抽奖」有活动在跑（本店 1 条：每天 14:00）。

**② 赠送专场卡** — 弹窗标题「专场卡」，列：名称 / 描述 / 有效期 / 操作（选 择）。
数据来自「计费设置 → 基础设置 → 专场卡」tab。本店 7 张：
5小时包时、专场卡（2h）、18-20点、上午、下午、早场卡9.9、5分钟测试专场卡。
**专场卡是「充值送时长」的唯一正规做法**（188VIP套餐 就是满 50/100/150 各送一张 2 小时专场卡）。

**③ 赠送商品** — 弹窗标题「选择商品」，列：勾选框 / 商品分类 / 商品名称 / 商品单位 / 商品图片。
只有一个「商品名称」搜索框 + 搜索/清空，**没有分类筛选**；默认 10 条/页（记得切 100，铁律 #12），
本店 38 条：饮料 19 / 小食品 9 / 香烟 5 / 酒水 5 / **服务 1**。

> 🔴 **权益商品（服务类）也在可选列表里** —— 「服务 / 洗浴 1 次 / 次」可以直接当充值赠品。
> 也就是说「充 50 送一次洗浴」这种服务型充值礼包是配得出来的，不必绕道发券。
> （商品清单里**没有「网费」类商品**，所以送网费金额这条路走不通，见下面 §2.5.1。）

选中后表单里那一行长这样：`洗浴 1 次    数量：[1] − +  ⊗`
- **数量默认 1**，`−` / `+` 调整，右侧圆形 `⊗` 是移除该商品（不是删整档）
- 商品行只显示名称和数量，**不显示图片缩略图**（选得对不对靠名称核对）
- 编辑页回填正常：名称、门槛、商品、数量、开关都在，可以正常改

列表「礼品内容」列的拼接顺序是 **抽奖在前、商品在后**：
实测配置「满 50 + 抽奖 1 次 + 洗浴 1 次 ×1」→ 列表显示 `充值满 50：抽奖1次，洗浴 1 次*1`
（商品用 `*数量` 后缀，专场卡只显示名字、不带数量）。

> ⚠️ **这是档位制，不是累进制。**
> 「充值满 X 元」是一组并列的门槛，不是「每满 X 元自动加一次」。
> 想表达「每满 50 送 1 次」，只能用多档去逼近（50/100/150/200/250/300 → 1/2/3/4/5/6），
> 代价是 **6 档上限、300 元以上封顶 6 次**。
> 多档之间到底是「命中最高的那一档、只发一份奖品包」还是「逐档累加」，**没有实测过**
> （要验证得真实充值，测试环境做不到）。**跟客户讲的时候必须说清这一点，不能拍胸脯保证累加。**

#### 接口明文，可以直接核对数据

查看详情时 `POST /business-wy/activitiesInfo/detail`（**是 POST，不是 GET**；用 GET 会返回
`406 非法访问`，裸 fetch 同理，见铁律 #3）返回 **明文 JSON**，用来复核配置最可靠。
取法：先 `goto` 到 `...&openType=view` 页 → `playwright-cli requests | grep detail` 拿序号 →
`playwright-cli response-body <序号>`。

```
activityName / type=9（充值赠送）/ status=1 开启 / openStartTime 00:00:00 openEndTime 23:59:59
prizeList[]  ← 一档一条
  ├ cash          = 充值门槛（元）
  ├ name          = "充值满50元"（系统自动拼）
  └ prizeRelationList[]   ← 一档里挂几样就几条，sort 决定顺序
      ├ prizeType = 4        ← 「赠送抽奖 N 次」
      ├ prizeNum  = N        ← 送几次 / 送几个
      ├ prizeName = "赠送抽奖1次"
      └ prizeId   = 商品赠品才有（指向商品 id）
```

**prizeType 编码表（三种都实测过）**：

| prizeType | 含义 | 实测来源 |
|---|---|---|
| 1 | 商品（实物 / 权益 / 服务都算） | 洗浴 1 次，`prizeId=2117087219679371266` |
| 2 | **赠送网费**（金额在 `gift` 字段） | 礼包「30元赠送网费」`gift=30`，见 §3.5 |
| 3 | 专场卡 | 188VIP套餐 三档各一张「专场卡」 |
| 4 | 抽奖次数 | 赠送抽奖1次 |

> ⚠️ `prizeType=2`（赠送网费）**在充值赠送活动里选不到**，只在礼包（§3.5）里出现 ——
> 两套配置共用同一套 prizeType 编码，但可用子集不同，别混。

### 2.6 商品优惠券 `/memberActivityManage/coupon`

两 tab：**优惠券** / **赠送规则**。这两个是一套东西的两半，只看一半会以为「配了没效果」：

```
优惠券    = 券的模板（满多少减多少、谁能用、多久过期）
赠送规则  = 券的发放开关（消费满 X 元自动送 N 张，带生效/失效时间）
```

🔴 **只建券不建规则 = 一张也发不出去。** 券躺在库里，收银台不会自动给。
反过来规则必须挂在已有券上（`优惠券` 下拉只能选「优惠券」tab 里已存在的）。

页面是 **avue-crud**（`.avue-form`），不是别处的 `el-form-item` 手写表单，
但字段结构仍是 `el-form-item`，控件还是 Element Plus，抓取方式不变。

#### 2.6.1 优惠券 tab（券模板）

列表列：优惠券名称 / 一次消费金额 / 可抵扣金额 / 适用场景 / 适用用户 / 有效期（天|固定日期）/ 操作（编辑 · 删除）。
**没有状态列** —— 券本身没有开关，能不能发完全由「赠送规则」决定。

「新 增」弹窗（标题就是「新 增」，avue 通用弹窗）：

| 字段 | 必填 | 控件 | 说明 |
|---|---|---|---|
| 优惠券名称 | ✅ | 文本，50 字 | placeholder `请输入 优惠券名称` |
| 一次消费金额 | ✅ | 数字 | **用券门槛**：消费满这个数才能用这张券 |
| 可抵扣金额 | ✅ | 数字 | 面额。**必须小于门槛**，否则等于白送 |
| 适用场景 | ✅ | 下拉 | ⚠️ 本店**只有「商超」一项**（见下） |
| 适用用户 | ✅ | 下拉 | 只有「会员」「所有」两项 |

#### 3.3.4 🔴 四个坑

1. **「活动总参与名额」新建时默认填着 1**，不改就是**整场活动全店只能参与 1 次**，活动等于废掉。

2. **「单用户最大参与次数」空 = 不限**。默认值不稳（有时是 1），建议显式填 `1`，

3. **保存后不跳列表、toast 常为空、URL 停在上一页**（实测连跑 4 条 URL 都没变）。

4. **状态「未开始」不等于没建成**。开放时间设 14:00，上午去看全是「未开始」，

### 3.4 商品促销 `/netBarActivity/promote`

活动管理下的「商品促销」tab（同级：整点抽奖 / 积分活动 / 游戏活动 / 礼包设置）。
作用在**商超商品**，与上网费、区域计费无关。

列表列：`# / 活动名称 / 活动类型 / 商品类型 / 折扣 / 活动时间 / 是否过期 / 状态 / 创建时间 / 操作`，
按钮：搜 索（只按活动名称）/ 清 空 / 添 加。**「添 加」跳独立页**，不是弹窗：
`/netBar/addActivity?actType=promote`
查看/编辑同一页带 `&id=<id>&openType=view|edit`。

#### 表单全字段（2026-11-02 实测）

| 字段 | 必填 | 说明 |
|---|---|---|
| 活动名称 | ✅ | 上限 50 字，右侧实时计数 `N / 50` |
| 活动类型 | ✅ | **限时折扣** / **多件折扣**，仅两项 |
| 折扣价 | ✅ | 「限时折扣」= `[__] 折`；「多件折扣」= `满 [N] 件，打 [__] 折`，满件数默认 **2** |
| 活动开放规则 | ✅ | **每日 / 每周 / 每月 / 指定日期** 四档 |
| 活动日期 | 随规则变 | 每日→「每天开放」纯文字；每周→周一~周日复选+全选；每月→1~31 复选+全选；指定日期→起止日期选择器 |
| 活动开放时间 / 活动结束时间 | ✅ | 每日时段，默认 `00:00` / `23:59`。**这是每天的时间段，不是日期** |
| 排序 | ❌ | 数字，可空（落库 `sort: 0`） |
| 开启活动 | ✅（打星） | 开关，**默认关闭** |
| 活动商品 | ✅ | **指定商品 / 指定分类 / 全店商品** 三档 |

新建页底部只有「保存提交 / 返回」。**保存成功提示「新增成功」/「保存成功」并自动跳回列表**。

#### 🔴 折扣校验：0 和 10 都不行，最多 1 位小数

前端输入框**不拦**（填 11、9.95 都能打进框里，只靠旁边一行小字提示「(范围：0-10)」），
点保存才由校验拦下，错误文案固定为：

> 折扣最多1位小数,且在0-10之间不能为0和10

所以合法区间是 **0.1 ~ 9.9，且只能一位小数**。实测 11 和 9.95 都被拦、保存动作不出网。
好消息是「填 0 白送」「填 10 反向加价」这两条路走不通；坏消息是这条限制只有提交时才知道。

#### 🔴 开关 = 编辑锁，但「删除」没锁

和充值赠送（§2.5）不同，这里**关掉才出现「编辑」**，但开启状态下操作列是：

| 状态 | 操作列 |
|---|---|
| 开启（`status=1`，开关变绿） | 查看、**删除** |
| 关闭（`status=0`，开关灰） | 查看、编辑、删除 |

也就是**活动正在生效中也能一键删掉**，没有二次校验挡着。删之前先想清楚当天有没有在用。

#### 「查看」页是真只读

`openType=view` 下所有 input `disabled=true`、无「保存提交」，只有顶部「< 返回」。
要看配置就点查看，不会误改。

#### 接口明文：`POST /business-wy/goodsDiscount/list`

列表响应 `data[]` 一条一个活动。字段编码实测对齐如下：

| 字段 | 含义 | 取值 |
|---|---|---|
| `type` | 商品范围 | **0=指定商品、1=全店商品、2=指定分类** |
| `subType` | 活动类型 | **1=限时折扣、2=多件折扣** |
| `discount` | 折扣 | 字符串，**直接是折数**（`"9"` 就是 9 折，不是 0.9） |
| `buyQuantity` | 满几件 | 多件折扣生效；限时折扣固定 `1` |
| `goodsNum` | 商品数 | 指定商品时=件数；全店商品为 `""` |
| `status` | 开关 | 1 开 / 0 关 |
| `expire` | 是否过期 | 0 未过期 / 1 已过期（列表列直接读它） |
| `startTime` / `endTime` | 活动日期 | `2026-11-02 00:00:00` 形式 |
| `openStartTime` / `openEndTime` | 每日时段 | `00:00:00` / `23:59:59` |
| `week` | 每周规则 | 选「每周」时才有值，其余为空 |
| `categoryId` / `goodsData` / `ids` | 范围明细 | **列表接口一律返回空**，明细只在详情接口 `POST /business-wy/goodsDiscount/detail` 里 |

> 别被列表里的空值骗了：`goodsData:""` 不等于没配商品。要核明细必须调 `detail`。

详情接口（`detail`）的 `goodsData[]` 每个商品带：`goodsName / goodsCategoryId / goodsImage /
salePrice / internetFeePrice / integral / unitName / attribute / isPackage`。
**促销选择弹窗里看不到的价格，这里能拿到。**

#### 🔴 坑 1：选商品弹窗没有价格列

「选择商品」弹窗列只有 **商品分类 / 商品名称 / 商品单位 / 商品图片**，**没有销售价、没有库存**，
只能按「商品名称」模糊搜（没有分类筛选）。40 条商品只显示单位不显示价格。

要定「打几折」，必须先切到 `销售管理 → 商超管理 → 商品管理` 查原价，
或者调 `goodsDiscount/detail` 看 `salePrice`。**只看这个弹窗定折扣，等于闭眼定价。**

图片列基本全空（图片挂在「商品名称」字典上，见 `07-商品销售.md` §2.4.2），别指望靠缩略图认货。

#### 🔴 坑 2：切换商品范围会清空已选

「指定商品 → 指定分类 → 全店商品」来回切，之前选好的商品/分类**立即清空、变「请选择商品」**，
且没有提示。定好折扣再动范围，别先选后改。

#### 🔴 坑 3：列表把「指定分类」写成「指定类型」

UI 下拉叫「指定分类」，列表「商品类型」列却显示 `指定类型 (1)`。
同一件事两个叫法，对账时别当成两个功能。三档的列表显示分别是：
`指定商品 (N)` / `指定类型 (N)` / `全店商品`（全店不带数量）。

#### 「指定分类」弹窗

标题也叫「选择商品」，但内容是 8 个分类的清单：服务 / 酒水类 / 积分兑换 / 外设租赁 / 套餐 / 香烟 / 饮料 / 小食品，
列 `分类 / 图片`，可多选、表头有全选框、可按分类名搜、每页 10 条。

#### 线上体检（南充测试场所，2026-11-02）

- 商品促销列表 **0 条**，等于线上没有任何商超折扣在跑。
- ⚠️ 抽查 4 个商品，**进货价全部 `0.00`**（红牛/乐虎/冰红茶/魔芋爽），只有销售价是正常值。
  → 成本核算、毛利、「预估成本」都没法自动算，只能手填。
- 🔴 **红牛销售价是 `0.01` 元**（同类：乐虎 3.00、冰红茶 1L 4.00、魔芋爽 5.00）。
  这条是异常数据，疑似早前测试残留。若照此价卖且再打 9 折 = 0.009 元/罐，纯亏。
  配任何促销前先修这条。

#### 未验证（别当成结论）

- 折扣到底作用在 `salePrice`（现金价）还是 `internetFeePrice`（会员网费售价）——
  商品同时有这两个价，接口另有 `discountOnline` / `discountWallet` / `walletPayment` 三个空字段，
  疑似「线上价/钱包价单独折扣」，但本账号界面上没暴露开关。**只能在收银端实测**。
- 与会员等级折扣、商品优惠券、团购券**是否叠加**，后台看不出来，需收银端对照小票。
- 「是否过期」到点后开关会不会自动关：未实测（改动结束日期到过去的操作没走完）。

### 3.5 礼包设置 `/netBarActivity/giftPackage`

**礼包 = 一个奖品包，自己不会发。在哪里被用：会员促销 → 策略设置（8 类人群）里的「礼包设置：选择礼包」**，
策略按人群自动/手动发券时才把礼包里的东西发出去。`基础设置 → 会员等级` 页**没有**礼包字段（只读，无此列），
所以礼包只有一个消费方。

列表列：礼包名称 / 礼包内容 / 预估成本 / 创建时间 / 操作（编 辑 / 删 除）。筛选：礼包名称。按钮：新增。
**「新增」是弹窗**（不是跳页），标题「新 增」，底部「保 存 / 取 消」；编辑是同一弹窗，标题「编 辑」、按钮「修 改」。

| 字段 | 控件 | 说明 |
|---|---|---|
| 礼包名称 | 文本框 | 必填 |
| 礼包内容 | 三个控件，见下 | **专场卡 或 赠送网费（二选一）+ 商品（可叠加）** |
| 预估成本 | 数字框 | **手填**，不按进货价自动算；编辑回填成两位小数（`20.00`） |

「礼包内容」一行长这样：

```
专场卡： [+ 选择专场卡]     或     赠送网费：[请输入] 元
商品：   [+ 选择商品] (最多9个)
```

#### 🔴 「或」是真的 —— 卡和网费同时填，网费会被静默丢掉（2026-11-02 实测）

实测：专场卡选「5小时包时」+ 赠送网费填 50 → 点保存提示「添加成功」，
但列表礼包内容只显示 `5小时包时`，**编辑回填时网费框是空的**，接口里也只剩一条 `prizeType=3`。
全程**没有任何校验提示**，填的时候两个控件都是可用的（不禁用），非常容易踩。

- ✅ **网费 + 商品** 可以共存：实测 `30元赠送网费，红牛*1`，接口两条（`prizeType=2` + `prizeType=1`）。
- ❌ **专场卡 + 网费** 不能共存：只留专场卡。
- ⚠️ **专场卡选定后按钮消失、只剩一个 `<span class="card-item">` 文本**，点它没反应，
  既不能换卡也不能清空 —— **选错只能删礼包重建**。选卡前想清楚。

「礼包内容」列的拼接规则：网费写 `N元赠送网费`，专场卡写卡名，商品写 `名称*数量`，多项用逗号分隔
（`30元赠送网费，红牛*1`）。

#### 接口：`POST /business-wy/activityGiftpack/list`（明文）

```
id / name / estimatedCost
prizeList[]
  ├ prizeType = 2 → 赠送网费，金额在 gift 字段（prizeName = "赠送30元网费"）
  ├ prizeType = 3 → 专场卡（prizeName = 卡名）
  └ prizeType = 1 → 商品，prizeId 指向商品，prizeNum = 数量
```

#### 实测：这家店线上 3 条礼包有 2 条名不副实

| 礼包名称 | 实际配置 | 问题 |
|---|---|---|
| 免费上网5小时 | 专场卡「5小时包时」 | 正常 |
| 到店赠送100元网费、红牛一杯 | **只有** `赠送100元网费` | 名称写「红牛一杯」，**商品没配** |
| 29.9元100 一杯饮品 | **只有** `29.9元现金网费(70.1元赠送网费)` | 名称写「一杯饮品」，**商品没配** |

→ 礼包名是自由文本、和内容**没有任何绑定校验**，改内容不会改名。
做活动复盘/对账时**以内容列为准，不要以名称为准**；反过来配置时也别信名字。

**删除有二次确认**：`确定将选择数据删除?`（取消 / 确定）。被策略引用的礼包能不能删，**未验证**。

## 四、典型配置流程

### 场景 A：唤回流失会员

1. 规则设置里确认「休眠人群」的判定星期
2. 促销人群 → 流失预警，看名单是否非空
3. 策略设置 → 对应人群 → 新增当前策略（给折扣或券）
4. 商品优惠券 → 新增券（门槛 + 抵扣 + 天数）
5. 促销历史 → 进行中，确认已生效

### 场景 B：充值拉新

1. 计费设置 → 充值活动方案（只读，确认基础档位）
2. 会员促销 → 充值赠送活动 → 添加（限时 + 礼品）：档位填「充值满 X 元，赠送抽奖 N 次」，
   一档还能同时挂专场卡和商品；最多 6 档。**配之前先看列表里有没有旧的占位活动还开着**
   （例如「充值满 0.01 元送抽奖 1 次」），旧的没关会把新规则完全冲掉。
3. 网吧配置 → 充值策略，确认「网民自助购买」开关
4. 会员等级 → 确认充值积分倍率是否也一起给

### 场景 C：日常活跃

1. 活动管理 → 积分活动 → 签到活动设置，配每日签到赠送
2. 转盘抽奖 → 配置消耗积分与次数上限
3. 礼包设置 → 配一个低成本礼包做签到大奖

## 五、红线

- 券/礼包**发出即不可撤回**，测试只用 1 个账号 1 张。
- 「不参加人群」会覆盖一切策略，配之前先看名单里有没有正常会员。
- 充值赠送与充值活动方案**可能叠加**，配第二个前先算总赠送率，超过 30% 要报老板。
- 商品促销改折扣后，检查商品原价是否被改成促销价（促销应打折，不是改原价）。

## 六、校验清单

| 检查项 | 期望 |
|---|---|
| 人群名单是否非空 | 空名单 = 策略不触发 |
| 策略是否在有效期内 | 过期策略在「已结束」里 |
| 券有效期天数是否合理 | 误填 3650 等于永久 |
| 转盘四项限制是否齐全 | 缺一项抽不了 |
| 礼包成本是否手填正确 | 系统不自动算 |
| 积分等级与计费等级是否混淆 | 两套体系，别互相套 |
