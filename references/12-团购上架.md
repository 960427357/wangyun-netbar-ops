# 旺云商户端 · 团购套餐创建与上架 v1

> 路由前缀 `/marketManage/groupManagement`、`/marketManage/verificationManagement`。
> 状态：2026-10-30 实测，**真实写操作**——新建套餐「69元享120元网费」并上架旺云商城，已刷新复核。
> 门店「演示门店」placeCode 00000000000000。

## 一、四个页面的分工（顺序不能乱）

| 顺序 | 页面 | 路由 | 干什么 |
|---|---|---|---|
| ① | 团购套餐 | `/marketManage/groupManagement/group` | 造券：名称、图片、现金网费 + 赠送网费、适用人群 |
| ② | 上架管理 | `/marketManage/groupManagement/publish` | 选平台、填门市价/团购价/库存，**真正对外可售** |
| ③ | 上架历史 | `/marketManage/groupManagement/putHistory` | 查上架/下架流水 |
| — | 团购授权 | `/marketManage/verificationManagement/groupBuy` | 平台授权（核销管理下，非团购管理） |

**关系：套餐是"货"，上架是"摆上货架"。** 只建套餐不上架 → 列表显示「暂未上架任何平台」，用户买不到。
上架前必须先有套餐，所以「先在团购管理里新增，再到上架页上架」，顺序反了没有可选项。

## 二、① 新建套餐（团购套餐 → 新 增）

实测字段：

实测字段（2026-10-30 二次核对，全量）：

| 字段 | 必填 | 控件 | 默认 | 说明 |
|---|---|---|---|---|
| 套餐名称 | 是 | input | — | 把价格写进名字，如「9.9元享30元网费」，用户一眼看懂 |
| 宣传图片 | **是** | 上传 | — | 750×400 横图。不传不让保存 |
| 套餐详情图片 | 否 | textarea | — | 长图/富文本区，纯网费券可空 |
| 补充信息 | 否 | textarea | — | placeholder「补充信息」，可空 |
| 现金网费 | 是 | number | 空 | placeholder「现金」。**用户实付能当网费用的部分**＝团购价 |
| 赠送网费 | 是 | number | 空 | placeholder「请输入」。`现金 + 赠送 = 券面总额` |
| 有效期设置 | 否 | radio | 相对时间 | 相对时间 / 指定时间；选相对时间时右侧填天数（默认 30） |
| 使用时间限制 | 否 | radio | 全部时间可用 | 全部时间可用 / 部分时间不可用；选不可用要填禁用的时段 |
| 团购使用时间 | 否 | 时间输入 | 00:00:00 | 配合上一项 |
| **使用限制** | 否 | radio | 所有用户 | 所有用户 / 新会员 / 老会员 —— 这就是列表里的「适用人群」 |
| 单人核销次数 | 否 | radio | 不限制 | 不限制 / 限制数量（选限制要填次数） |
| 套餐内容挂载 | 否 | 4 个「选择…」按钮 | — | 核销套餐 / 礼品套餐 / 专场卡 / 商品，纯网费券**不要挂** |

**「仅限新会员」= 把「使用限制」单选到 `新会员`**，不是表单外的开关。上架后列表「适用人群」列会显示「新会员」。

**金额怎么填**（关键，容易填反）：

> 需求「69 块享受 120 网费」→ 现金网费 `69` + 赠送网费 `51` = 120。
> 需求「9.9 块享受 30 网费」→ 现金网费 `9.9` + 赠送网费 `20.1` = 30（带小数时两位相加要精确到角）。
> 列表「套餐内容」列会自动显示成 `69元现金网费+51元赠送网费`，这就是校验点。

**不要点「选择核销套餐」等 4 个按钮。** 纯网费券不需要挂任何内容物，挂了反而限制使用范围。
只需：填名称 → 传图 → 填两个数字 → 保存，返回「添加成功」。

保存后列表「操作」列出现 `编 辑 / 详 情 / 删 除`，说明是本店新建的（系统预置的只有 `详 情 / 删 除`）。

## 三、② 上架到平台（上架管理 → 上/下架）

流程共 **4 次点击**，少一次都不落库：

1. 找到套餐行 → 点「上/下架」→ 弹出**上/下架弹窗**，列出各平台当前状态。
2. 点目标平台行的「上 架」→ 右侧滑出**「套餐上架旺云商城」抽屉**。
3. 填三项必填 → 点抽屉底部「上 架」→ 弹出**确认框**「确认信息无误，请点击提交按钮」。
4. 点确认框的 **「提交」**（⚠️ 不是「确定」）→ 落库。

抽屉字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| 门市价格 | 是 | 券面价值（原价），本例 `120` |
| 团购价格 | 是 | 用户实付，本例 `69` |
| 库存 | 是 | **店规：一律 `9999`**，不要自拟 |
| 销售时间 | 否 | 下拉，默认「不限制」，保持默认 |

平台行（本店实测两个）：

- **旺云商城**，服务费 `4‰`，走旺云自有商城，已可上架。
- **美团**，当前未上架；上架前需先在「核销管理 → 团购授权」完成授权，否则点了也上不去。

成功标志：

- 列表「销售平台」列变成 `旺云商城 已上架 团购价：￥69 销售时段： 不限制`；
- 重开上/下架弹窗，平台行 `￥120 / ￥69 / 9999 / 已上架 / 不限制`，操作列变 `下 架 / 详情`；
- 抓包能看到 `POST /business-wy/listInfo/add` 返回 200。


## 三之二、设推荐 / 设热门（上架列表行内）

套餐上架后，列表里有「推荐」「热门」两列，是平台侧的运营位（首页/列表排序加权），
**只有已上架旺云商城的套餐有意义**。

| 项 | 做法 |
|---|---|
| 设为推荐 | 点该行的 `设为推荐`，立即生效，无确认框，`POST /business-wy/listInfo/setRecommended` |
| 设为热门 | 点该行的 `设为热门`，同上，`POST /business-wy/listInfo/setHot` |
| 成功标志 | 同一位置文案变成 `取消推荐` / `取消热门`（红色），并弹「操作成功」 |
| 取消 | 再点一次，变回灰色 `设为推荐` / `设为热门` |

两个是独立开关，互不影响。用 `scripts/set-recommend-hot.js`（`ACTION = recommend | hot | both | none`）。

**坑：点完列表会整体刷新，目标行会短暂消失（约 1-2 秒）。** 此时立刻去读行内容会拿到 null，
误判成"没找到这一行"；连续点推荐→热门时会因为读不到行而漏掉第二个开关。必须轮询等行回来再操作。

## 四、坑（按踩坑概率排序）

1. **平台行列表偶尔是空的。** 打开上/下架弹窗后平台表格一片空白，不是你点错，是接口没回来。
   处理：关弹窗 → **整页重载** → 重来，最多重试 4 次（`scripts/publish-groupon.js` 已内置）。
   只等待不重载通常也救不回来。
2. **确认框按钮是「提交」不是「确定」。** 按「确定」写脚本会找不到元素，表现为"点了没反应、
   没提示、状态不变"，极容易误判成接口失败。确认框文案：`确认信息无误，请点击提交按钮 / 取消 / 提交`。
3. **点「上 架」后必须先有确认框，才说明按钮真的被点到。** 若连确认框都没弹，是点击没落到按钮上
   （弹窗遮罩/抽屉滚动位置），重试。
4. **只建套餐不上架 = 白干。** 上架管理页里 `暂未上架任何平台` 是默认状态，不是失败。
5. **门市价与团购价别填反。** 填反了用户会看到"原价 69、现价 120"。改法：下架 → 重新上架重填。
6. **库存不要自拟。** 店规统一 `9999`。
7. 本店历史套餐（含预置的）团购价多为 `￥0.01`，那是测试数据，**不要照抄当模板**。

## 七、宣传图规范（750×400）

券图是给顾客看的，**店名错了比排版难看严重得多**。

| 项 | 规定 |
|---|---|
| 尺寸 | 750×400 横图（上传框按此比例，竖图会被裁） |
| **场所名** | **必须实时读取，禁止写死。** 见下方说明 |
| 主数字 | 实付价，超大号；`69` 用 132px，`9.9` 这类带小数的用 108px，同一字号会挤压「元」 |
| 金额拆分 | 副行写「网费 X 元 ＋赠送 Y 元」，两数相加必须等于券面额（69+51=120、9.9+20.1=30） |
| 人群标签 | 所有用户 → 橙胶囊「新老会员均可购买」；新会员 → 紫胶囊「仅限新会员」。**必须与券的「使用限制」一致** |
| 底部 | 「旺云商城团购券 · 数量有限 售完即止」 |

### 场所名怎么取（核心，换店不改脚本）

登录后右上角（`.el-header`）里第一段纯文本**就是场所名**，其后的「管理员」「AI 旺，您的智能助手」
是固定项。实测本店返回：

```json
["演示门店", "管理员", "AI 旺，您的智能助手"]
```

`scripts/make-groupon-banner.js` 已内置读取 + 过滤：

```js
const skip = /^(管理员|超级管理员|店长|收银员|AI 旺.*|退出|退出登录|首页|消息|设置)$/;
const shop = all.find(t => !skip.test(t) && t.length <= 40) || '';
if (!shop) return 'FAIL: 未能从右上角读到场所名…';   // 取不到就停，绝不回退硬编码
```

**为什么不能写死**：这套技能是给多家网吧共用的。写死的店名只有本店对，换一家店就会把
别家顾客引到错的招牌上；而且本店后台改过名之后，旧图也立刻失真。
早期版本就写死成「示例网咖」，与后台真实名称「演示门店」不符，已修。

**取不到就报错退出，不要兜底。** 兜底一个默认店名会让错误静默通过，
生成一张看得清、但店名错的图，比生成失败更危险。

### 出图后必须核对

用截图工具看一眼，确认三件事：文字不重叠、不裁切、主数字与「元」不挤压。
机器能自动判的只有尺寸，排版只能眼看。

## 八、查销量：哪个套餐卖得好

> 2026-10-31 实测。「我的团购券哪个卖得好」这类问题的**唯一正解就在这一页**，
> 但口径有三个坑，直接念数字会答错。

**位置**：团购管理 → **上架管理**（`/marketManage/groupManagement/publish`）。
`scripts/read-groupon-sales.js` 跑一次拿全量排行，不用手点。

### 8.1 表格结构（9 列，顺序固定）

| # | 列 | 备注 |
|---|---|---|
| 0 | `#` | 行号，**不是**套餐 id |
| 1 | 套餐名称 | 即团购券名 |
| 2 | 套餐内容 | `X元现金网费+Y元赠送网费`，可能带换行（含实物时） |
| 3 | 销售平台 | 多行：平台名 / 已上架｜暂未上架任何平台 / `团购价：￥N` / 销售时段 |
| 4 | 适用人群 | 所有用户 / 新会员 / 老会员 |
| **5** | **销量** | **就是这一列**，纯数字，无单位 |
| 6 | 推荐 | `设为推荐` / `取消推荐`（红） |
| 7 | 热门 | 同上 |
| 8 | 操作 | `上/下架`、`套餐详情` |

- **销量取 `td[5]`**，按表头文字定位更稳：`heads.indexOf('销量')`。
- 团购价要从**第 3 列文本里正则抠** `￥([\d.]+)`，没有独立的价格列。
- 未上架的套餐第 3 列只有「暂未上架任何平台」一行，抠不到价格 → 记为 null，别当 0 元。

### 8.2 🔴 三条口径（页面顶部原文，答之前先念一遍）

1. **销量仅统计上架到旺云商城的销量，不包含上架到美团的销量。**
   → 问「团购总共卖了多少」时，这是**旺云商城单渠道**的数，美团那边要另外去美团商家后台看。
2. **销量是历史累计，页面没有任何时间筛选。**
   → 这张表**答不了「本月 / 本周卖了多少」**。筛选栏只有 4 项：
   `套餐名称 / 销售平台 / 推荐状态 / 热门状态`，**没有日期**。
3. **下架不清零。** 实测有套餐显示「暂未上架任何平台」却仍带 3 单销量——
   销量跟着套餐走，不跟着上架状态走。所以「当前在架的销量」需要自己按「已上架」过滤后重算。

### 8.3 页首另外两条（容易被忽略，但影响运营动作）

- **设为推荐 → 展示在旺旺宝网吧版首页，只能设置一个。**（同时设两个，后设的顶掉前一个）
- **设为热门 → 展示在支付宝小程序，可多个。**

### 8.4 交叉验证：销量 vs 核销

销量 = **卖出去**，核销 = **用掉了**。两者不等是常态，差值就是「已售未用」。

| 页面 | 路由 | 看什么 |
|---|---|---|
| 上架管理（本页） | `/marketManage/groupManagement/publish` | 销量（卖出） |
| 核销记录 | `/marketManage/verificationManagement/gruopWriteOff` | 核销流水（用掉） |
| 核销总览 | `/marketManage/verificationManagement/summary` | 核销汇总 |
| 团购总览（预售） | `/marketManage/groupManagement/wangyunPreSale` | 预售汇总，**默认时间范围常是当天，容易读到 0** |

- 核销记录**每页 10 条**，得按 `.el-pager li` 翻页抓全量再自己聚合（`cnt by 券名`）。
  该页**没有**「销量」列，只有流水，聚合口径是**条数**不是金额。
- 核销记录里团购名列在 `td[3]`；**2025 年的老记录该字段可能是空串**，
  别把空串当成一个套餐去排榜（聚合时归到「(空)」并单独说明）。
- 团购总览读到 0 不一定是真没生意，先确认时间范围。

### 8.5 三个必须一起看出来的异常

脚本已经把这三类自动列在 `异常` 里，回答时要一并说，否则给出的「第一名」是假的：

| 异常 | 含义 |
|---|---|
| **零销量但有货** | 券在架上没人买 → 价格/曝光/人群限制有问题 |
| **未上架却有销量** | 销量是累计的，说明下架前卖过；不能当「当前在售」讲 |
| **有销量但团购价 ≤￥0.01** | 疑似测试价。**这种「卖得好」不是生意好，是价格被改成 1 分钱** |

实测（示例门店 2026-10-31）：7 个套餐、总销量 27。榜首「老会员冲50送20」14 单占 52%，
但它的团购价是 **￥0.01**（券面 50 现金 + 20 赠送）；真正按正常价卖的两张
（￥9.9 享 30、￥69 享 120）**销量都是 0**。核销 26 条里 24 条集中在同一会员、跨一年，
**整批基本是内部测试记录**。→ 结论不能只说「第一名卖得好」，必须点明价格异常。

### 8.6 脚本

```bash
playwright-cli run-code --filename scripts/read-groupon-sales.js
```

自动做的事：进页 → 按表头定位「销量」列 → 翻页抓全量 → 按销量降序 →
算占比 → 标出三类异常。输出 `套餐数 / 总销量 / 排行[] / 异常{} / 翻页[]`。

## 九、团购券设置：把抖音/美团券绑到系统内容（核销管理 → 团购券设置）

> 路由 `/marketManage/verificationManagement/groupSet`
> ⚠️ **在「核销管理」下，不在「团购管理」下** —— 十条里九条找错模块。
> 状态：2026-11-01 实测（真实门店，含一次真实同步）。产品方（旺云商户端开发工程师）口述流程。

### 9.1 它到底干什么

**抖音/美团上新一张券，系统里不会自动知道这张券该给顾客什么。** 这一页就是「翻译官」：
把平台券（只有名字和价格）翻译成系统的发放内容（网费 / 专场卡 / 礼品套餐 / 商品）。

- **不绑定的后果**：券照样能卖，但顾客来核销时系统没有可发的东西，现场只能手工补，
  且销售总览、提成、交接班全都对不上这张券。
- **它是「一张券一份内容」**，不是全局规则；同一个「39.9 抵 100」在抖音和美团是两行，要分别绑。

### 9.2 页面结构（avue-crud，不是普通 el-table）

|---|---|
| 筛选 | 平台（`抖音` / `美团`）、团购状态（实测只有 `售卖中` 一个选项）、`搜 索` / `清 空` |
| 列（8 列） | 团购名称 / 平台 / 团购状态 / 身份限制 / 单人核销次数 / 使用时间 / 团购内容 / 操作 |

> 右上角「同步线上数据」是一个 **`span.el-button--text.syncbtn`，不是 `<button>`**。

### 9.3 第一步：点「同步线上数据」（从平台拉券）

> 🔴 **铁律：每一次进来动手之前，先点一次「同步线上数据」。**（产品方强调）
> 不点同步，你看到的是**上次同步时的快照**——平台上新上的券根本不在列表里，
> 平台上改过价、改过名的券，本地还是旧名字。**在旧快照上绑内容，等于给一张已经不存在的券配货。**
> 所以「同步」不是可选的准备工作，它是**每次进场的第 0 步**：进来先同步 → 再看列表 → 再绑。

**同步本身没有二次确认**，点完约 **1.5~2 秒**弹 toast「**同步成功**」，列表自动重载。
（注意：**同步没有**二次确认，但**保存绑定有**，见 §9.6.1。）

接口（抓包实测）：

| 动作 | 接口 |
|---|---|
| 同步 | `POST /business-erppro/thirdCoupon/synProduct` |
| 拉列表 | `GET /business-erppro/thirdCoupon/getCouponGoodsList?param=<密文>` |

#### ⭐ 实测到的四个同步行为（这一段最重要）

1. **券名称会被平台最新名称覆盖。** 同步前 `『周年庆』『暑期』【新用户专属】39.9抵100网费（未开户）`
   → 同步后 `【新用户专属】29.9抵100网费（未开户）`（店方在平台改了价，本地跟着变）。
2. **平台已经没有的券，本地列表里会消失。** 本次两条旧券（`138享338`、`早鸟特惠9.9`）同步后不见。
3. **已绑定的内容不会被覆盖。** 名称变了、内容还是原来那份 —— 这就是坑的来源：
   `【通用】49.9享70网费` 的内容仍是 `48.1元现金网费+21.9元赠送网费`，
   **券名 49.9、实际只给 48.1 现金**，必须人工重绑。
4. **重复点同步是幂等的。** 第二次同步 10 条 → 10 条，不重复插入。

> 🔴 **所以顺序只能是：同步 → 名称有了 → 按名称逐条绑内容。**
> 反过来（先绑内容再同步）会被名称变更打乱，且下架券会带走绑定。

### 9.4 第二步：按名称绑内容（网费券换算）

**网费券的公式（产品方口述）**：`X 抵 Y` / `X 享 Y` → **现金网费 = X，赠送网费 = Y − X**，两者相加等于 Y。

| 券名（平台） | 现金网费 | 赠送网费 | 合计 |
|---|---|---|---|
| 39.9 抵 100 | 39.9 | 60.1 | 100 |
| 48.1 享 70 | 48.1 | 21.9 | 70 |
| 99 享 150 | 99 | 51 | 150 |
| 138 享 338 | 138 | 200 | 338 |

**校验口诀：现金就是顾客实付，赠送 = 券面 − 实付。** 两个数字之和必须等于券名里的那个数。

> 本店实测反例：`【新用户专属】29.9抵100网费（未开户）` 绑成 `29.9 + 70.1 = 100` ✔；
> 而 `【通用】49.9享70网费` 绑成 `48.1 + 21.9 = 70`，**总额对、本金少 1.8 元** ✘ ——
> 总额对不对不能当验收标准，**现金必须等于顾客实付**。

### 9.5 使用限制怎么判（直接看券名，产品方口述）

| 券名里出现 | 使用限制选 | 说明 |
|---|---|---|
| **新老通用 / 新老共享 / 通用** | `不限制` | 谁都能用 |
| **新会员 / 新用户 / 新客** | `限新会员` | 只给没开过卡的 |
| **老会员** | `限指定等级会员` | 选完还要勾「会员等级」（见 9.6） |

实测印证：`【新老通用】48.1享70网费` → 身份限制列显示「不限制」；
`【新用户专属】39.9抵100网费` → 显示「限新会员」。

> ⚠️ `『老会员特享』138享338` 当初挂在「不限制」，名字与设置不符（该券本次同步后已消失，
> 若平台再上，按「限指定等级会员」处理）。

### 9.6 编辑弹窗「团购关联」全字段（6 项）

| # | 字段 | 控件 | 选项 / 联动 |
|---|---|---|---|
| 1 | 团购名称 | 只读文本 | 平台来的名字，**不能改** |
| 2 | 团购平台 | 只读文本 | `抖音` / `美团` |
| 3 | 使用限制 | 下拉 | `不限制` / `限新会员` / `限指定等级会员`  ← 选第三项会**多出「会员等级」复选** |
| 3.1 | 会员等级 | 复选 | `所有等级` / `VIP` / `MJZS` / `砖石会员` / `普通[计费]` / `天王` / `黄金会员`（**店自建等级，换店会变**） |
| 4 | 单人核销次数 | 下拉 + 数字 + 下拉 | `不限制次数` / `限制次数为` → `[1]` 次 + 限制时间 `每日 / 每周 / 每月 / 每年 / 不限时间` |
| 5 | 使用时间 | 下拉 | `不限制时间` / `限制每周` → 周一~周日复选 + `请选择使用时间`（时间段） |
| 6 | 团购内容 | 四类 | `选择礼品套餐` ｜ `专场卡：选择专场卡` ｜ **或 网费：[现金] 元，赠送 [赠送] 元** ｜ `商品：选择商品（最多 9 个）` |

**未绑定券打开弹窗时长这样**：三个下拉全是 `请选择 …`，网费两个框为空 —— 这就是「待绑定」。

> 🔴 **三个下拉全部是必填**（`is-required`）：使用限制 / 单人核销次数 / **使用时间**。
> 第三个最容易被当成「可选项」漏掉，**漏了就点不动保存**（详见 §9.6.2）。

#### 🔴 判「绑没绑」：`团购内容` 列既不能为空，也不能带 `*数字`

**不要用「三列都是 `--`」当判据**（v1.6.8 曾这么写，v1.6.9 实测推翻）：

| 内容列长相 | 真相 | 该做什么 |
|---|---|---|
| 空 | **待绑定** | 三个下拉 + 网费，从头填 |
| `X元现金网费+Y元赠送网费` | **绑的是网费（正确）** | 只核金额，不改结构 |
| **`某某*1` / `某某*3`** | **绑的是商品（商品代网费）** | 删商品 → 改填网费（§9.13） |
| **纯卡名**（`双人套餐` / `单人套餐一`），无 `*数字` | **绑的是专场卡** | **只提示不改**（§9.15，铁律 #29） |

第三行是 v1.6.38 新增的判据：`*1` 表示「一个叫这名字的商品，数量 1」，
顾客核销只拿到一张商品券，网费不进账。**名字长得像网费（`30元得35元网费`）也一样是商品。**

第四行是 v1.6.40 新增：**专场卡和网费是「或」关系**，绑了专场卡，网费两个框 `disabled`。
`畅享6小时 / 4小时` 这类时长券本来就该给时长卡，**不要当成「网费 0 元」去改**。

实测反例：`【新用户专属】29.9抵100网费（未开户）` 列表里「单人核销次数」显示 `--`，
但内容是 `29.9+70.1`，**是绑好的**。打开它的编辑弹窗，**整页只有 5 个字段，
「单人核销次数」这一项根本不渲染**——后端该字段为空时前端直接不显示，不是列表渲染问题。
→ 老会员/新会员券的弹窗都可能是 5 项，**别拿「字段少了一个」当异常**。

#### 9.6.1 保存机制：点「确定」之后还有一道确认框（v1.6.9 实测）

**这是本轮踩得最久的一个坑**：点弹窗的 `确 定` 之后，**不会立刻提交**，
而是弹出一个 `el-message-box`：

> **提示**
> 请确保已在团购平台内容中，充分说明团购内容
> `取消` `确定`

必须**再点这个确认框的 `确定`**，才会真正发出保存请求。

| 阶段 | 现象 |
|---|---|
| 点弹窗 `确 定` | **无请求、无 toast、弹窗不关**（看起来像按钮失灵） |
| 点确认框 `确定` | 发出 `POST /business-erppro/thirdCoupon/bindGoods` → toast「**操作成功**」→ 两弹窗都关闭 |
| 点确认框 `取消` | 回到编辑弹窗，之前填的不丢 |

> 🔴 **判断「到底提没提交」只看两件事**：有没有 `bindGoods` 请求、有没有「操作成功」。
> **不要用「弹窗关没关」判断**——没点确认框时，弹窗会一直开着，很像卡死。
>
> 自动化脚本要抓 `el-message-box`，只监听 `el-message` / `el-notification` 会永远抓不到，
> 然后误判成「前端静默校验拦截」，一路去查表单必填项（本轮就是这么绕了四圈）。

接口（抓包实测）：

| 动作 | 接口 |
|---|---|
| 保存绑定 | `POST /business-erppro/thirdCoupon/bindGoods` |
| 拉列表 | `POST /business-erppro/thirdCoupon/getCouponGoodsList?param=<密文>` |

> 🔴 **联动坑（实测）**：把「使用限制」改成 `限指定等级会员` 时，
> **「单人核销次数」会被自动改成 `限制次数为`（默认 1 次）且限制时间未选**，
> 此时点「确 定」会提示「**请填写完整**」。改完使用限制一定要回头看一眼核销次数那一行。
>
> ⚠️ 未做空提交测试：三个下拉都不选直接点「确 定」是否被拦，**未验证**，不要拿它当「可以先存后补」。

#### 9.6.2 🔴 空必填下拉的失败长什么样（2026-11-09 实测，4 条连败）

**现象**：填了「使用限制」和网费，点「确 定」后 **确认框不弹、没有 `bindGoods` 请求、没有 toast、弹窗不关**。
连续 4 条全部如此，看起来像按钮失灵或登录态掉了，实际只是表单没填全。

**真实原因**：未绑定的券，「使用时间」也是空的。选了 `限制每周` 类的规则却没选具体时段，
或干脆三个下拉有一个空着，都会卡在校验。

**判据（按可靠性排序）**：

| 观察 | 结论 |
|---|---|
| `el-message-box` 没出现 | 校验未过，**一定没提交** |
| 没有 `POST /thirdCoupon/bindGoods` | 同上 |
| `.el-form-item__error` 有文字 | 能直接读到缺哪项（脚本里抓这个） |
| 「弹窗没关」 | **不能用来判断**，见 §9.6.1 |

**正确顺序（务必按这个次序设，否则前面的会被重置）**：

1. 使用限制（`不限制` / `限新会员` / `限指定等级会员`）
2. 单人核销次数（改第 1 步会把它重置成 `限制次数为`）
3. 使用时间（`不限制时间`）
4. 回读三项，**三个 placeholder 都不为空**再往下走
5. 清商品 → 填网费 → 确定 → 确认框确定

**两个不显眼的字段行为**：

- 使用限制选 `限新会员` 时，**「单人核销次数」这一项根本不渲染**（DOM 里查不到该 label），
  列表该列显示 `--`。这是系统行为，不是漏填，照样能保存成功。
- 使用限制选 `限指定等级会员` 时才会多出「会员等级」复选；本店口径**老会员券用 `不限制`**，
  不要走这条路。若已勾成 `所有等级`，列表会显示 `限指定等级会员（全部等级）`，与 `不限制` 不等价，
  要改回来只能再把使用限制切回 `不限制`。

### 9.7 包时券：先不绑，但必须提醒人工处理

通宵、时段包这类券（本店有 `12.8畅玩`→`通宵-大厅`、`19.9`→`通宵-单包`、
`39.9`→`通宵-双人包`、`9.9`→`早鸟特惠5小时-仅限大厅`），绑法走「专场卡 / 礼品套餐」，
**本轮不展开**，遇到先跳过、只处理网费券。

🔴 **规则是「先不绑」，不是「不用管」。** 每遇到一条都要记进「待人工处理」清单，
并在收口时明确报出来。两个理由：

- 包时券在列表里和网费券长得一样，`团购内容` 同样为空。事后没人分得清哪条是「故意跳过」、
  哪条是「漏绑」。跳过必须留痕，否则等于把问题藏起来。
- 包时券核销后直接影响上机时长和营业额，绑错比不绑更难收拾。绑法必须由人拍板。

清单长这样，收口直接贴：

| 券名 | 平台 | 团购内容 | 卡在哪 |
|---|---|---|---|
| 网咖3小时套餐 | 抖音 | 空 | 包时券，绑法待人工确认 |
| 【新老会员通用】早鸟卡畅玩4小时 | 美团 | 空 | 包时券，绑法待人工确认（另有一条重复行已绑「早场卡」） |

### 9.9 绑定 SOP（每来一张新券照这个走）

0. 🔴 **进场第一件事：点 `同步线上数据`** → 等 toast「同步成功」。**不做这步，后面全白做。**
1. 核销管理 → 团购券设置（`/marketManage/verificationManagement/groupSet`）。
2. 在列表里找 **`团购内容` 列为空** 的行 —— 那就是待绑定（判据见 §9.6，别看三列 `--`）。
3. 点该行 `编辑`，按 §9.5 判使用限制（看券名含「新老通用」还是「新会员」）。
4. 网费券按 §9.4 填 `现金(实付) + 赠送(券面−实付)`；包时券不绑，但**记进待人工处理清单**（§10.7）。
5. 「单人核销次数」保持 `不限制次数`（除非券名/平台规则明确限次）。
6. 「使用时间」保持 `不限制时间`（除非平台写了限时段）。
7. 点弹窗 `确 定` → 🔴 **再点确认框「请确保已在团购平台内容中，充分说明团购内容」的 `确定`**
   → 等 toast「**操作成功**」。
8. **回列表核对「团购内容」列**（显示成 `X元现金网费+Y元赠送网费` 才算落库）。
9. ⚠️ **每次同步后，把所有「名称里的价格」和「团购内容里的现金」对一遍** ——
   平台改价会改名字、但不会改绑定（§9.3 第 3 条）。

**批量核对可直接套用的校验式**（本轮用它一次扫全表）：

```js
// 券名抠 实付X 与 券面Y，内容抠 现金C + 赠送G
const m = name.match(/(\d+(?:\.\d+)?)\s*(抵|享)\s*(\d+(?:\.\d+)?)/);   // X, Y
const c = content.match(/(\d+(?:\.\d+)?)元现金网费\+(\d+(?:\.\d+)?)元赠送网费/); // C, G
// 两条同时成立才算对：现金 = 实付；现金 + 赠送 = 券面
ok = Math.abs(C - X) < 0.005 && Math.abs(C + G - Y) < 0.005;
```

### 9.10 一句话判断

只能看套餐卡内部是否自带网费，需人工跟店方对一次，**脚本无法判定，也不要去改**。

#### 本轮修掉的两个脚本 bug（都是第一次遇到这类数据才暴露）

1. **分页切 100 条/页没生效 → 17 条只读到 10 条。**
   旧判据是「`rows > 0` 且分页器出现『共』」，默认 10 条/页时立刻就满足了，
   在表格渲染前点的那次「100条/页」被吞掉也不报错。已改成
   **轮询到 `已渲染行数 >= 总条数` 才放行**，并且每 6 轮重试一次切页。
   → 与 SKILL「脚本写法硬规矩」第 5 条同源：**判据必须带数量，不能只判存在**。
2. **专场卡读成了按钮文本。**
   旧脚本用「找按钮文本包含『专场卡』」来读，实际绑好的卡是
   `span.card-item`，按钮永远是「选择礼品套餐」。所以 8 条专场卡全被读成 `(NO BTN)/(无)`，
   差点误判成「没绑内容」。已改为读 `.card-item` 文本 + `.card-info .icon-delete` 是否存在。

## 十、多场所批量核对（换场所 / 定期巡检照这个走）

> 状态：2026-11-01 第二场所（示例场所 002）实测，28 条券 / 3 页全量核对完成。
> 触发场景：**换了一个场所**、或对方说「把所有券重新绑一遍、检查一遍」。

### 10.1 券列表是「场所级」的，换场所等于换一套数据

一个账号下可以有多个场所，每个场所的团购券**各自独立**（同一账号在场所 A 配的绑定，
不会出现在场所 B）。所以：

- 🔴 **切换场所后必须重新点一次「同步线上数据」**，不能沿用上一个场所的列表。
- 🔴 **不要把场所 A 的核对结果当场所 B 的结论**——两边券名、价格、条数全不一样
  （示例：A 场所 10 条，B 场所 28 条）。
- 确认当前场所：读 `.el-header` 的 innerText（实测输出形如 `示例区某某网咖 002`）。
  右上角那个下拉是**用户菜单**（用户信息/修改密码/退出登录），不是场所切换器，别点错。

### 10.2 读全表：先把「10 条/页」改成「100 条/页」，别硬翻页

分页默认 **10 条/页**，页面底部形如 `共 28 条 10条/页 1 2 3 前往 页`。
那串 `10条/页` **是个下拉**（选项 10/20/30/40/50/100），改它比翻页靠谱得多：

```js
// ⭐ 首选：切 100 条/页，一页读完（28 条 → 1 页，翻页代码全省了）
await page.locator('.el-pagination__sizes .el-input, .el-pagination .el-select').first().click();
await page.locator('.el-select-dropdown__item').filter({ hasText: /100/ }).first().click();
await page.waitForTimeout(1500);
// 回读第一行，确认真的重渲染了，再开始读表
```

为什么优先这个：

| | 逐页翻 | 切 100 条/页 |
|---|---|---|
| 28 条券 | 3 次点击 + 3 次等待 | 1 次，读完 |
| 漏检风险 | 点空 / 点到旧页码 / 等待不足 → **静默读重页** | 只有「没切成功」一种风险，且回读即可发现 |
| 行序稳定性 | 翻页时列表若按销量重排，跨页会**串行** | 一次快照，不存在跨页串行 |

⚠️ **两种情况下还是得翻页**：① `共 N 条` 里 N > 100（如 `共 128 条` → 100 条/页仍要 2 页）；
② 该页分页条上没有 `el-pagination__sizes`（页面没开 sizes 属性）。兜底写法：

```js
const n = await page.locator('.el-pager li').count();   // 页数
for (let k = 0; k < n; k++) {
  await page.locator('.el-pager li').nth(k).click();
  await page.waitForTimeout(1800);
  // 读 tbody tr → 8 列
}
```

> 🔴 **只读第一页就下结论是最常见的漏检**：B 场所 18 条待核对里，有 **5 条**在后两页，
> 其中 2 条完全是空的（待绑定）。第一页看起来「基本都绑好了」，翻完才发现漏一半。
> 改页容量这一步，就是把「会不会漏」这个问题一次性消掉。

#### 实测记录（2026-11-01，场所A，28 条券）

| 验证项 | 结果 |
|---|---|
| 下拉选项 | 实测就这 6 档：`10条/页 20条/页 30条/页 40条/页 50条/页 100条/页` |
| 切之前 | `共 28 条 10条/页 1 2 3 前往 页`，表格 **10 行** |
| 切之后 | `共 28 条 100条/页 1 前往 页`，表格 **28 行**，页码区自动从 `1 2 3` 收缩为 `1` |
| 顺序 | 切完第一行仍是 `【新老会员通用】早鸟卡畅玩4小时`，末尾是 `【007全新升级 直播间复利】99享308元网费`，**没有重排** |
| **交叉验证** | 逐页翻 3 页（10+10+8=28 行）与一次读全的 28 行**逐行完全相同**（含顺序），双向差集 0 条 |
| **是否记忆** | ❌ **不记忆**。`reload` 后回 10 条/页；重新 `goto` 进菜单也回 10 条/页 → **每次进页都要重切** |
| 别的页面 | 核销记录 `gruopWriteOff` 也有该下拉，切换生效；团购管理-套餐页 **无分页条**（走例外 ②） |

> 「页码区从 `1 2 3` 变成 `1`」是最快的成功判据——比数行数还快，一眼就知道切上了。

⚠️ 因为没有持久化，「上午已经切过一次」这个记忆不能带到下一次操作。读表前**固定动作**：
先看页脚有没有 `100条/页`，没有就切。

### 10.3 一次扫全表的校验脚本（直接抄）

```js
// name: 团购名称, content: 团购内容
const m = name.match(/(\d+(?:\.\d+)?)\s*元?\s*(?:抢|抵|享|得)\s*(\d+(?:\.\d+)?)/);   // 实付X, 券面Y
const c = content.match(/(\d+(?:\.\d+)?)元现金网费\+(\d+(?:\.\d+)?)元赠送网费/);     // 现金C, 赠送G
ok = Math.abs(C - X) < 0.005 && Math.abs(C + G - Y) < 0.005;
```

> 🔴 **正则里的 `\s*元?\s*` 不能省。** 券名有两种写法：`29.9抢100网费`（无「元」）
> 和 `29.9元抢35元网费`（有「元」）。只写 `\s*(?:抢|抵|享|得)\s*` 时，带「元」的券
> **匹配失败 → 被归为「非网费券」直接跳过 → 不校验也不报错**。
> 实测 28 条里就漏了 1 条（`【007全新升级.通用】29.9元抢35元网费`），补上 `元?` 后
> 网费券从 18 条变 **19 条**。**先看「识别出的网费券条数」对不对，再看校验结果**，
> 否则「全部通过」可能只是「大部分没被检查」。

**这一步能抓出人眼很容易漏的错**：B 场所有一条 `【新会员专享】29.9抢100网费`，
内容填的是 `29.9 + 701`——**赠送多打了一位数（70.1 → 701）**。人眼看「有个 70 开头」就过去了，
但校验式一算 `29.9 + 701 = 730.9 ≠ 100`，立刻暴露。已改为 `29.9 + 70.1`。

### 10.4 B 场所（28 条）实测结论

| 类别 | 条数 | 处理 |
|---|---|---|
| 网费券已绑且正确 | 15 | ✔ 无需动 |
| 网费券**金额写错** | 1 | 🔧 `29.9抢100网费`：`29.9+701` → `29.9+70.1` |
| 网费券**完全空白** | 2 | ✅ 新绑：`39.9享100元网费`→`39.9+60.1`、`直播间复利99享308`→`99+209` |
| 包时券（3 小时 / 5 小时 / 早鸟卡 / 大厅套餐） | 5 | ⏭ 不绑，但**必须列入「待人工处理」清单**（见 10.7） |
| 福袋券（20 / 30 / 50 元网费） | 4 | ⚠️ **新类别，公式套不上，见 10.5**；同样进待处理清单 |
| 同名重复行 | — | 见 10.6 |

**18 条网费券全部通过**（`现金 = 实付` 且 `现金 + 赠送 = 券面`），0 条错误残留。

### 10.5 福袋券：名称里只有面值，没有实付价 —— 套不了公式

`福袋【20元网费】`、`福袋【30元网费】`、`福袋【50元网费】`（同名的有两条），
三列全 `--`、内容为空。

公式 `现金 = 实付` 的前提是**券名里能读出顾客实付多少**。福袋的名字只有「给多少网费」，
没有「卖多少钱」，所以：

- ❌ 不能想当然填 `现金 = 20、赠送 = 0` —— 那等于按面值送，可能远超实际收款。
- ❌ 也不能填 `现金 = 0、赠送 = 20` —— 现金为 0 会导致营业额、提成、对账全部归零。
- ✅ **正确做法：去平台上查这张福袋的实际售价，再做 `现金 = 售价、赠送 = 面值 − 售价`。**
  查不到就先挂着，**别猜**。

> 这是**第四个券类别**（网费 / 专场卡 / 礼品套餐 / 商品 之外的一种命名形态），
> 后续若常遇到，应在 §9.7 旁单列一节。

### 10.6 坑（B 场所新踩，5 条）

| # | 坑 | 说明 / 对策 |
|---|---|---|
| 1 | **同名券有多条** | `29.9抢35网费` 出现 3 条、`早鸟卡畅玩4小时` 出现 2 条（同步产生的重复行）。按名字定位会**永远改到第一条**，批量脚本要用行索引或 `nth()` |
| 2 | **同名两条，一条已绑一条空** | `早鸟卡畅玩4小时` 第 1 页那条已绑 `早场卡`，第 2 页那条是空的。包时券按约定跳过，但**要知道这不是漏绑，是重复行** |
| 3 | **已绑定券的弹窗只有 5 项** | 无「单人核销次数」项（该字段为空时前端不渲染）。改金额时**只碰两个数字框**，别去动下拉，否则会把使用限制重置 |
| 4 | **数字错位比手误更常见** | `70.1 → 701`、`5.1 → 51` 这种多打/少打一位，合计校验一算就露。**必须跑校验式，人眼核对不可靠** |
| 5 | **限制时间 `--` 的券优先怀疑未绑** | B 场所 4 条福袋的「使用时间」也是 `--`（其他空券是不限制时间）。`--` 出现在**使用时间**列，说明整行基本没配过 |
| 6 | **把「10 条/页」的当前页当成全部** | 页脚 `共 28 条` 才是真总数，屏幕上的 10 行只是一页。**进页第一件事改页容量到 100**（§10.2），别先读表再想起翻页 |

### 10.7 跳过包时券必须留痕，收口必须提醒

包时券本轮不绑，这一点不变。变的是一句话的收尾方式：**从「跳过」改成「跳过并报出来」**。

#### 判定词表（命中任一即视为包时券）

`小时` / `通宵` / `包夜` / `早鸟` / `畅玩` / `大厅套餐` / `单人包` / `双人包` / `五人包` / `专场卡`

⚠️ **命名陷阱**：`【任意时间】5小时网费畅玩（仅限五人包）`、`网咖5小时畅玩套餐` 这类名字里
带「网费」「畅玩」，看起来像网费券。**只要出现「X 小时」，就按包时券处理，不能套网费公式**
（`5 小时` 没有 `X 抢 Y` 的实付和券面，公式根本算不出来，硬填就是瞎猜）。
判定顺序固定为 **先看有没有「X 小时」，再看 `抢/抵/享/得`**。

#### 收口必须包含的三块

| 块 | 内容 | 缺了会怎样 |
|---|---|---|
| ① 已处理 | 改了哪几条，改前 → 改后 | 对方不知道动了什么，无法抽查 |
| ② 校验结果 | 网费券 N 条全过；有错就贴明细 | 「都正常」这种口径等于没校验 |
| ③ **待人工处理** | 包时券逐条列名 + 福袋券逐条列名 + 各缺什么 | **跳过变成隐藏，下次还得重新发现一遍** |

#### 反面例子（这条要避免）

> ❌「包时券 5 条按约定跳过，其余全部正常。」
>
> 问题：对方只知道「有 5 条」，不知道是哪 5 条、在哪一页、有没有绑过。等下次巡检时，
> 这 5 条仍要靠人重新扫一遍才发现，等于这次没留下任何可用信息。

✅「待人工处理 9 条：包时 5 条（网咖3小时套餐 / 网咖5小时畅玩套餐 / 【通用特惠】新老会员3小时大厅套餐 /
【新老会员通用】早鸟卡畅玩4小时 ×2），福袋 4 条（20/30/50/50 元网费，缺平台售价）。
包时券需要定绑法，福袋券需要给售价，给我就能一次绑完。」

### 10.8 一句话判断

> **换场所 = 换一整套券 = 重做同步 + 页容量切 100 一次读全 + 跑校验式 + 把跳过的列出来。**
> 「上一家都绑对了」这件事，对下一家没有任何参考价值。
> 跳过的券不列出来，等于没做这一步。
