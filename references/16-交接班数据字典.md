# 16 · 交接班数据字典（七区块 × 接口字段）

> 用途：把「交接班 → 查看」这一页从"看四个金额"升级成"能拆到单品、能对库存、能算人效"。
> 前置：`09-门店资料.md` §7 讲的是入口、口径与对账三坑；本文讲**每个区块到底有什么字段、怎么算、哪里会骗人**。
> 实测样本：2026-10-31 示例网咖（连锁 A 店）的代管账号，三条班次已逐字段核对。

## 一、入口与三个接口

| 层 | 地址 | 备注 |
|---|---|---|
| 列表 | `/netBarSummary/handOver` | 默认最近 7 天、10 条/页；**无导出按钮** |
| 详情 | `/netBar/handOverDetail?id=<GUID>` | **SPA 同页跳转**，不是新标签、不是弹窗 |
| 数据 | `GET /business-wy/shiftChange/shiftDetail?param=<密文>` | 返回**明文 JSON**（约 13.8KB），param 加密 |

列表接口 `/business-wy/shiftChange/list`、汇总 `/business-wy/shiftChange/total` 的 `param` 也都是密文，
**不能靠改报文改参数**；要批量取数只能逐行点「查看」再拦截 `shiftDetail` 的响应。

点「查看」的正确写法（表格有固定列，DOM 里会出现 10 个同名按钮，只有前几个可见）：

```js
const btns = page.locator('button:has-text("查看")');   // 注意：没有空格
for (let i = 0; i < await btns.count(); i++)
  if (await btns.nth(i).isVisible()) { await btns.nth(i).click({ force: true }); break; }
```

抓响应（页面里 `fetch` 重放会 406，必须靠拦截）：

```js
const p = new Promise(res => page.on('response', async r => {
  if (r.url().includes('shiftChange/shiftDetail')) res(await r.text());
}));
await page.reload({ waitUntil: 'domcontentloaded' });
const body = await p;      // 明文 JSON
```

## 二、七个区块 ↔ 字段对照

### 2.1 班次抬头

| 页面 | 字段 | 说明 |
|---|---|---|
| 当班人员 | `classUserName` | 通常就是「收银员」这个账号名，**不是真人姓名** |
| 班次时间 | `startTime` → `endTime` | 上一班交班时刻 → 本班交班时刻。**08:4x~09:1x 结尾 = 夜班**，20:3x~20:5x 结尾 = 白班 |

### 2.2 金额卡片（8 项）

| 页面 | 字段 | 口径 |
|---|---|---|
| 本班上缴现金 | `upPayment` | 交给店里的现金 |
| 上班预留 | `lastSpareSum` | 上一班留给本班的备用金 |
| 留给下班 | `reserveMoney` | 本班留钱箱的备用金，**实测长期 0** |
| 总收入 | `totalIncome` | = 现金 + 移动 + 核销 |
| 现金收入 | `cashIncome` | = 网费现金 + 商品现金 |
| 移动收入 | `onlineIncome` | = 网费微信/支付宝 + 商品微信/支付宝 |
| 核销收入 | `verifyTotalAmount` | 美团 + 抖音 + 旺云商城 |
| 团购预收入 | `groupBuyPerSaleAmount` | 团购预售未核销部分，实测 0 |

### 2.3 网费充值（3 汇总 + 9 明细）

| 页面项 | 字段 |
|---|---|
| 网费充值(现金) / (微信) / (支付宝) | `rechargeXj` / `rechargeWx` / `rechargeZfb` |
| 散户押金(现金) / (移动支付) | `depositTempXj` / `depositTempMobile` |
| 散户上网收入(现金) / (移动支付) | `tempNetFeeIncomeXj` / `tempNetFeeIncomeMobile` |
| 会员充值收入(现金) / (移动支付) | `memberRechargeXj` / `memberRechargeMobile` |
| 连锁会员充值收入(现金) / (移动支付) | `chainMemberRechargeXj` / `chainMemberRechargeMobile` |
| 起步费充值 | `startingFee` |

`rechargeXj = depositTempXj + tempNetFeeIncomeXj + memberRechargeXj + chainMemberRechargeXj + startingFee`（实测成立）。

> **这条链路暴露一个事实**：这家店三班全部是「连锁会员充值」，散户押金、散户上网、普通会员充值**全 0**。
> 即顾客都走「连锁会员」通道充值上机，没有散客直接投币上机。

## 三、四条恒等式（2026-10-31 实测全通过）

```
现金收入 = 网费充值(现金) + 商品(现金)
移动收入 = 网费充值(微信+支付宝) + 商品(微信+支付宝)
总收入   = 现金收入 + 移动收入 + 核销收入          （上缴金额不参与加总）
核销收入 = 美团 + 抖音 + 旺云商城

【库存】前班库存 − 当前库存 = 销售数量 + 换购数量 + 报损 − 吧台出入库 − 跨班次回补
【原料】前班库存 − 当前库存 = 原料销售 + 原料报损
```

库存恒等式实测 21 条分类记录：其中 3 条「中式纯茶」因成品零库存不适用（见 §五），
其余 18 条中 17 条完全闭合，1 条差 1 件（夜班 10/30-31 的香烟@槟榔，实减 7 / 应减 8）。

## 四、商品模块六个易混列怎么读

| 列 | 计不计销量 | 计不计金额 | 扣不扣库存 | 实测样本 |
|---|---|---|---|---|
| 正常销售 `saleQty` | 计 | 计 | 扣 | 快乐肥宅水 2 个 16 元 |
| 换购 `hgNum`/`hgPrice` | **不一定**（有「售 0 额 5.0 换购 1」） | 按换购价计（也有按原价计的情况） | **扣** | 枸杞槟榔(紫气东来) 58→换购 8 元；枸杞槟榔30元 售0 额5 换购1 |
| 积分兑换 `exchangeNum` | 计 | 记在 `exchangeTotalPrice` | 扣 | 三班全 0（商城刚配） |
| 活动兑换 `winningNum` | 计 | 0 | 扣 | 三班全 0 |
| 会员余额 `memberPrice` | 计 | 从余额扣，不进现金/线上 | 扣 | 三班全 0 |
| 报损 `bsNum` | 不计 | 不计 | 扣 | 三班全 0 |

**结论：做「卖得最好的商品」排行，分子要用 `saleQty + hgNum + exchangeNum + winningNum`，
只取 `saleQty` 会漏掉换购单**（实测「枸杞槟榔30元」整单换购时销量记 0，金额却是 5 元）。

## 五、原料：茶饮是「成品零库存 + 茶包扣减」

实测「中式纯茶」这类现制茶饮：

- 分类里的**前班库存 / 当前库存经常是空值或 0**，前端显示 `--`，但照样卖出 1 / 2 / 5 杯；
- 真正的成本核算是**原料表扣茶包**，一对一对应：

| 成品（分类：中式纯茶） | 原料 |
|---|---|
| 花毛峰 / 绿毛峰 | 花毛峰茶包 / 绿毛峰茶包 |
| 养肝护肝茶 | 养肝护肝茶包 |
| 润肺养生茶 | 润肺养生茶包 |
| 蜜桃乌龙冷泡茶 | 蜜桃乌龙茶包 |
| 青提乌龙冷泡茶 | 青提乌龙茶包 |

所以**对茶饮做「库存对账」永远对不上**（库存恒 0，销量 > 0），必须换成「出杯数 = 茶包消耗量」来核。
反过来，茶包消耗量与出杯数不等，就是漏记或报损未登。

## 八、三个会骗人的字段

| 字段 | 现象 | 处理 |
|---|---|---|
| `goodsIncome` | **与 `goodsIncomeXj+Wx+Zfb+Wallet` 以及分类合计都对不上**：实测差 42.0 / 8.0 / 31.0（三班各不相同，且找不出规律）。页面不展示此字段 | **一律不用**。商品收入用四栏之和，商品总额用 `categorySaleInfo` 求和 |
| `verifyAmount` | 空字符串 `""`（旧字段） | 用 `verifyTotalAmount` |
| `lastSpareSum` / `reserveMoney` | 长期 0.00 | 钱箱零备用金，下一班找零要自己垫，需在备注中提示 |

另：`saleQty` 对换购单的处理不一致（同为换购，有的计销量有的不计），跨班次比较销量时要注意。

## 十一、这些数据能干什么（运营动作清单）

| 数据 | 动作 |
|---|---|
| 核销占比 41.4%，抖音一家独大（430~820/班） | 抖音券是主渠道，注意佣金与结算周期；美团只占零头，可加大美团投放做制衡 |
| 商品结构：烟+槟榔一班占 58%（186/322） | 烟槟榔是现金流担当但毛利薄；把「泡面+饮料+咖啡」做成夜间套餐提毛利 |
| 积分只发不收（3 天 2660 分，0 消耗） | 立刻推积分商城兑换（20 款商品已配），否则积分变成纯负债 |
| 租赁 23 次/夜、收入 0 | 给外设配租金（押金+2 元/次），或改成「满 4 小时免费借」做差异化 |
| 茶包消耗 vs 出杯数 | 每天核一次，出杯 > 茶包消耗说明漏记原料，反之是报损未登 |
| 中式纯茶库存恒 0 | 别再拿库存报表质问店长，茶饮用原料表核 |
| 白班/夜班差 1.85 倍 | 夜班人力可以压缩（1 人足够），白天加强 |
| 留给下班长期 0 | 每班固定留 200 元备用金，写进交接班制度 |

## 十二、脚本

`scripts/read-handover.js`：
从当前页（列表页或详情页）进入第一行/指定行的交接班详情，拦截 `shiftDetail`，
输出对账摘要 + 商品 Top + 租赁 + 原料 + 异常项，可直接 `JSON.stringify` 落盘做月报。

```bash
playwright-cli run-code --filename=scripts/read-handover.js   # ROW=0 表示第一行
```

## 十三、坑清单

1. 「查看」按钮文字是 `查看`（**无空格**），和「搜 索」「清 空」不一样。
2. 详情页是 SPA 同页跳转，`page.goBack()` 才能回列表；直接 `goto` 列表会重新加载并重置筛选。
3. 页面里直接 `fetch` 接口会 **406**（缺前端加签），只能拦截响应。
4. 分类表里 `lastBarAmount` / `barAmount` 可能为空字符串，前端显示 `--`，别当 0 参与计算。
5. `rentInfo` 为空数组时页面「租赁统计」整块不出现，不代表没有设备，只代表本班没人借。
6. 分页只有 2 页（13 条/7 天），改时间范围后**必须点「搜 索」**才生效。
